## 1. 量体适配层（MeasureProvider）

### 1.1 为什么必须有这一层

采购 SDK 会带来三个必然问题：各家输出的围度字段名不同、部位覆盖不同、精度特性不同（有的腰腹准、有的四肢准）。如果业务代码直接吃厂商返回值，换一家就是全面重写。适配层要做的就是把这些差异全部吸收在一个模块里。

### 1.2 接口定义

```python
class MeasureProvider(ABC):
    code: str                      # 供应商标识，写入 body_measurements.provider_code

    @abstractmethod
    def measure(self, req: MeasureRequest) -> MeasureResult: ...

    @abstractmethod
    def health(self) -> ProviderHealth: ...

    @abstractmethod
    def unit_cost(self) -> Decimal:   # 单次调用成本，用于成本监控与分流决策
        ...

@dataclass
class MeasureResult:
    measurements: dict[str, float]    # 必须已归一到标准字段字典
    confidence:   dict[str, float]    # 0~1，缺失部位不出现在 dict 中
    mesh: bytes | None                # glTF/GLB
    raw: dict                         # 厂商原始返回，只用于排查，不进业务逻辑
```

### 1.3 适配器的四项职责

1. **字段映射**：厂商 `bust` / `chest_circumference` / `胸围` 一律映射到标准 key `chest`。映射表配置化，不硬编码。
2. **单位与口径统一**：统一 cm、一位小数；区分净体围与含衣松量（有的 SDK 默认给"着装围"，要减去经验修正量）。
3. **缺失部位补全**：厂商没给的部位，用回归模型从已有围度 + 身高体重推算，并把 `confidence` 打低（≤0.5）标记为推算值。**推算值必须可区分**，否则会污染精度评估。
4. **异常拦截**：明显不合理的输出（腰围 > 胸围 + 40cm、身高与输入偏差 > 5cm）直接判失败并转降级路径，不要把离谱数据写库。

### 1.4 多供应商分流与 A/B

```
分流决策（配置中心 cfg_flags: measure.provider_routing）
  ├─ 强制指定（灰度名单 / 内部测试）
  ├─ 按 user_id 稳定哈希分桶（A/B，保证同一用户始终同一家，数据才可比）
  ├─ 健康度熔断（某家错误率 >5% 或 P95 >40s，自动摘除）
  └─ 成本保护（当日预算用尽时切换到低价供应商或强制手动建档）
```

每家供应商独立统计：调用量、成功率、P50/P95 耗时、单次成本、**在标定集上的部位级误差**、**用户手动校正率**。最后一项是最真实的线上精度指标——用户改得越多，说明算得越不准。

### 1.5 精度验收方法（POC 阶段执行）

1. 招募 ≥200 名志愿者，覆盖性别、BMI（含 BMI>28 的胖体与 <18 的瘦体）、身高分布。
2. 由同一名专业量体师用软尺按统一标准测量，作为 ground truth；每人测两遍取均值以控制人工误差。
3. 同一批照片喂给各供应商，计算 **MAE（平均绝对误差）、P90 误差、系统性偏差（bias）**。
4. 分层看结果：**胖体和特殊体型的误差往往是均值的 2 倍以上**，而这恰恰是本产品的高价值用户群。只看整体均值会选错供应商。
5. 验收线：胸/腰/臀 MAE ≤ 2.0cm 且 P90 ≤ 3.0cm；长度类 MAE ≤ 1.5cm。

## 2. 尺码表解析与归一化管线

这是整条链路上**最脏、最容易被低估**的一环。淘宝尺码表的现实是：图片格式、字段叫法混乱、单位混用、平铺与围量混淆、还有大量"手动测量误差 1-3cm"的免责声明。

### 2.1 管线

```
输入（三种来源）
  ├─ 官方 API 结构化数据 → 直接进归一化
  ├─ 商品详情图 / 用户截图 → 图像预处理 → 表格检测 → 单元格 OCR → 表格还原
  └─ 用户手填 → 直接进归一化（信任度最高，但要做合理性校验）
        │
   ┌────▼──────────────────────────────────────────┐
   │ 归一化                                          │
   │ 1. 品类识别（标题+图片 → category_code）         │
   │ 2. 取该品类的 field_template（含 alias_dict）    │
   │ 3. 表头字段映射：中文别名 → 标准 key            │
   │ 4. 尺码标签归一：M/均码/165/90A → 统一 + 排序    │
   │ 5. 口径判定：平铺 or 围量（见 2.2，最关键）       │
   │ 6. 单位换算（cm/inch）                          │
   │ 7. 合理性校验（见 2.3）                          │
   └────┬──────────────────────────────────────────┘
        │ confidence ≥ 阈值 → 入库可用
        └ confidence < 阈值 → 入 adm_review_tasks 人工审核 + 前端提示用户确认
```

### 2.2 平铺 / 围量判定（最高优先级的正确性问题）

判错会让推荐结果差一倍，比"没有推荐"更糟。判定依据按可靠性排序：

1. **表头文字**：出现"衣宽/胸宽/半胸围/1/2胸围"→ 平铺；"胸围/围度"→ 需进一步判断。
2. **数值量级**：上衣胸围字段若在 45–70 之间，几乎必然是平铺半宽；若在 85–130，是围度。这条简单规则能解决大部分情况。
3. **与同类商品分布比对**：同品类同尺码的历史数据分布，偏离 3σ 则可疑。
4. **尺码表中的示意图**：有平铺示意图的一般是平铺量法（P2 再做图像判别）。

任何一步存疑，**宁可降级为"该部位不参与推荐并告知用户"，也不要猜**。

### 2.3 合理性校验规则

- 同一字段随尺码递增必须**单调不减**，否则判定 OCR 串行/串列。
- 相邻码差值应在合理区间（胸围档差通常 2–5cm），异常跳变触发审核。
- 必填字段缺失比例 > 50% → `parse_status = partial`，前端明确提示"该商品尺码信息不全，推荐仅供参考"。
- 数字与单位分离错误（如 "108" 识别成 "1O8"）用正则 + 数值域拦截。

### 2.4 OCR 技术选型

自建（PP-Structure 系表格识别）+ 云厂商通用表格 OCR 双通道，取置信度高者；两者分歧大时进人工队列。人工审核的结果**回流成为训练/校准样本**，这是解析成功率从 60% 爬到 85% 的唯一途径。

## 3. 尺码推荐引擎

### 3.1 整体公式

对每个候选尺码 `s`，计算各部位的合身分，加权得到总分：

```
FitScore(s) = Σ_p w_p · PartScore(p, s)   /   Σ_p w_p

PartScore(p, s) = f( ease_actual(p,s) , ease_ideal(p) , ease_min(p) , ease_max(p) )

ease_actual(p,s) = garment_cm(p,s) · k_flat(p) + bias(brand, category, p)
                   - body_cm(p) · (1 + preference_adj(p))
```

各项含义：

| 项 | 来源 | 说明 |
| --- | --- | --- |
| `garment_cm` | `cat_size_entries.values` | 成衣尺寸 |
| `k_flat` | `cat_field_templates.measure_mode` | 平铺需 ×2 |
| `bias` | `cat_brand_bias` | 品牌偏差修正，样本不足时为 0 |
| `body_cm` | `body_measurements` | 用户净体围度 |
| `preference_adj` | 用户偏好（tight/regular/loose） | 一般 ±3%~5% |
| `ease_*` | `cfg_ease_rules`（品类 × 版型 × 弹性 × 部位） | 松量区间 |
| `w_p` | 同上 | 部位权重 |

### 3.2 PartScore 的形状（分段函数，不是线性）

```
         分数
         100 ┤        ┌──────────┐
             │       /            \
          70 ┤      /              \
             │     /                \
           0 ┤────┘                  └────
             └────┬────┬──────┬─────┬────► ease_actual
              ease_min  ideal-δ  ideal+δ  ease_max
```

- 落在理想区间内 → 满分。
- 向两侧衰减：**偏紧的衰减速度必须显著快于偏松**。穿不进去是硬失败，偏松只是不好看——这个不对称是推荐体验的关键。
- 超出 `ease_min`：对高弹面料允许负松量（弹性 high 时 `ease_min` 可到 -6cm），无弹面料直接 0 分并标 `too_tight`。

### 3.3 部位权重（示例，实际由 `cfg_ease_rules.weight` 配置）

| 品类 | 高权重部位 | 说明 |
| --- | --- | --- |
| 衬衫 | 胸围 0.35、肩宽 0.30、袖长 0.20、衣长 0.15 | **肩宽是硬约束**，肩不合身没有任何补救办法 |
| T恤 | 胸围 0.45、衣长 0.25、肩宽 0.20、袖长 0.10 | 针织宽容度高 |
| 裤装 | 腰围 0.35、臀围 0.30、裤长 0.20、大腿围 0.15 | 腰臀差大的人是重灾区 |
| 连衣裙 | 胸围 0.30、腰围 0.25、臀围 0.25、裙长 0.20 | |
| 外套 | 胸围 0.30、肩宽 0.30、袖长 0.20、衣长 0.20 | 需考虑内搭余量，`ease_ideal` 比衬衫大 8-12cm |

> **硬约束机制**：肩宽（上衣）、腰围（裤装）设为一票否决项——不满足最小要求时，无论总分多高都判 `no_fit`，并直接给出"该商品所有尺码都不建议"的结论。敢说"别买"，才是真正有价值的推荐。

### 3.4 置信度计算

```
Confidence = min( C_body , C_chart , C_rule ) × C_margin

C_body   = 相关部位测量置信度的加权最小值
C_chart  = 尺码表解析置信度 × 品牌 trust_score
C_rule   = 该品类规则的成熟度（有无足够反馈样本支撑）
C_margin = 最优码与次优码分差的归一化（分差小 → 说明模棱两可 → 置信度降低）
```

置信度 < 0.5 时，前端不展示"推荐 L"这种确定性结论，改为"L 或 XL 都可以试，差异主要在胸围"这类模糊表述。**宁可示弱，不可误导**——一次错误推荐造成的信任损失，需要十次正确推荐才能补回来。

### 3.5 冷启动与降级矩阵

| 缺失情况 | 降级策略 |
| --- | --- |
| 用户只有身高体重 | 用人群统计模型估算围度，置信度上限 0.6，明确提示"建议拍照建模以提升准确度" |
| 尺码表只有 2 个字段 | 只比对已有部位，结论标注"仅基于胸围判断" |
| 品类无模板 | 用通用模板，比对所有能对上的字段，置信度打 0.7 折 |
| 无品牌偏差数据 | bias = 0，不做修正 |
| 完全无尺码表 | 不给推荐，引导用户手动录入或提示"该商品信息不足" |

### 3.6 反馈驱动的参数迭代（半自动）

```
每周批任务：
  聚合 fb_fit_feedbacks（按品类/品牌/部位）
    ├─ 若某品牌某部位系统性反馈"偏小"且样本 ≥30 → 生成 brand_bias 调整建议
    ├─ 若某品类"偏松"反馈占比 >40% 且样本 ≥100 → 生成 ease_ideal 下调建议
    └─ 若某供应商某部位的校正量持续同向 → 生成建模偏差修正建议
  ↓
  所有建议进入后台待审列表（J-5），由运营/打版师确认
  ↓
  确认后生成新 rule_set 版本 → 10% 灰度 → 对比采纳率与退货率 → 全量或回滚
```

**绝不自动改规则。** 反馈数据里混杂着用户主观偏好、购买错码、商家发错货等噪声，自动调参会被噪声牵着走。

## 4. 试穿可视化

### 4.1 MVP 方案：形变贴合，不做物理仿真

真实布料仿真（XPBD）在移动端实时跑不动，MVP 采用近似方案：

1. 服装用**参数化模板网格**（每品类每版型一套），按成衣尺寸对模板做分段缩放。
2. 用**蒙皮绑定**把服装网格绑到人体网格，按人体形态形变贴合。
3. 检测穿透，向外推出到人体表面 + 面料厚度。
4. 计算每个顶点的"拉伸量"= 贴合后周长 / 原始服装周长，映射为热力图颜色。

效果上不如真实仿真好看，但**热力图的准确性只依赖尺寸计算，不依赖仿真质量**——而热力图才是决策依据。这是有意识的取舍。

### 4.2 热力图配色（需与设计统一）

| 状态 | ease 范围（相对理想区间） | 颜色 | 文案 |
| --- | --- | --- | --- |
| 过紧 | < ease_min | 红 | 穿不进/绷紧 |
| 偏紧 | ease_min ~ ideal-δ | 橙 | 贴身，活动受限 |
| 合适 | 理想区间 | 绿 | 合身 |
| 偏松 | ideal+δ ~ ease_max | 浅蓝 | 宽松 |
| 过松 | > ease_max | 深蓝 | 明显偏大 |

色盲友好：颜色之外必须同时用**图案/文字标注**，不能只靠红绿区分。

### 4.3 渲染降级

设备分三档（按 GPU 型号 + 内存 + 实测帧率动态判定）：

| 档位 | 方案 |
| --- | --- |
| 高端 | 端侧实时 3D，可旋转缩放，60 FPS |
| 中端 | 端侧 3D，降低网格精度（LOD1）+ 关闭阴影，30 FPS |
| 低端 | 调 `render-svc` 服务端出图，返回 4 个角度的静态图 + 热力图 |

## 5. 效果评测体系

### 5.1 离线评测

| 对象 | 数据集 | 指标 | 频率 |
| --- | --- | --- | --- |
| 量体 | 200 人黄金标定集 | 部位 MAE / P90 / bias，**分 BMI 段** | 每次换供应商或版本 |
| OCR | 1000 张人工标注尺码表 | 字段准确率、表格结构准确率、口径判定准确率 | 每周 |
| 推荐 | 历史反馈回放集 | 推荐码与"用户反馈合适的码"的一致率 | 每次规则变更 |

> 三个黄金集都要**版本化并纳入 CI**：规则或模型变更后自动跑回归，指标下降超阈值即阻断发布。没有这道闸门，算法迭代就是盲人骑马。

### 5.2 在线指标

| 指标 | 定义 | 目标 |
| --- | --- | --- |
| 推荐采纳率 | 按推荐码下单 / 查看推荐 | ≥50% |
| 采纳后尺码退货率 | 采纳推荐且因尺码退货 / 采纳数 | ≤10% |
| 用户校正率 | 建模后手动改围度的用户占比 | ≤30% |
| 解析成功率 | parse_status=ok / 总解析 | ≥80% |
| 无法推荐率 | 因数据不足无法给结论 / 总请求 | ≤15% |
| 置信度校准度 | 高置信度推荐的实际正确率是否真的更高 | 单调相关 |

最后一项常被忽略但很重要：**如果标 0.9 置信度的推荐和标 0.6 的正确率差不多，说明置信度是假的**，用户会很快失去信任。

## 6. 二期（定制制版）算法预告

MVP 不实现，但接口与数据结构要预留：

- **参数化打版**：`净体尺寸 + 款式参数 + 松量规则 + 面料缩率 → 2D 版片`。基于成熟制版体系（文化式原型/国标比例法）建规则库，输出贝塞尔曲线描述的版片。
- **版片校验**：缝合边等长校验、袖山与袖窿吃势比（一般 8%–12%）、对位点、缝份加放、丝缕线标注。
- **导出**：DXF-AAMA（`ezdxf`）、PDF 分页、SVG。
- **排料**：启发式 + 遗传算法求解面料利用率，目标 ≥ 82%。
- **不可全自动**：所有自动版片进打版师工作台复核后才可投产（PRD G 节已明确）。
