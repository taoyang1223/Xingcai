## 1. 一句话路线

**模块化单体（Go）扛业务 + 独立算法服务（Python）扛视觉/OCR；C 端 Flutter，后台 React；数据 PostgreSQL + Redis；先 Docker Compose，后 K8s。量体、电商取数全部走可替换接口，第一期只实现「手动输入」这条实现。**

落地顺序只有一条：

```
锁技术路线（本文）
  → 搭仓库与骨架（能编译、能起服务、能打通健康检查）
    → 跑通「手填尺寸 + 手填尺码表 → 推荐码」（核心架构的第一条业务链）
      → 再接后台配置、OCR、量体 SDK、App、3D
```

**核心架构 ≠ 三个客户端同时开工。** 核心架构是：契约、模块边界、数据模型、推荐引擎、配置中心、防腐层。App / 3D / SDK 是挂在这套骨架上的端。

## 3. 为什么这样选（给评审用，日常开发不必反复讨论）

| 决策 | 理由 | 代价（接受） |
| --- | --- | --- |
| Monorepo | 团队小、三端要共用契约；拆多仓会把时间耗在发版对齐上 | 目录纪律必须严，CI 按路径过滤 |
| Go 模块化单体 | 业务模块调用密、事务多；算法才需要独立扩缩 | 必须用目录 + lint 防模块穿透 |
| Python 独立进程 | OCR / 量体适配在 Python 生态，且将来吃 GPU | 多一个进程，用 gRPC + 健康检查管住 |
| Flutter | 双端一套 UI，人力不够养两套原生 | 相机 / 3D / 厂商 SDK 必须走 Platform Channel |
| Riverpod | 和 Flutter 官方方向一致，异步三态清晰 | 团队统一，禁止再引入第二套状态库 |
| 手写 SQL + migrate | 尺码表、加密字段、版本快照不容 ORM 蒙 | 表结构变更必须双改：SQL +《02 数据库设计》 |
| Redis Stream 先顶 MQ | 内测量级用不到 Kafka；先把「任务接口」抽象出来 | 换 RocketMQ 时只改适配器 |
| Compose 先于 K8s | 骨架阶段要的是「本机能起全套」，不是编排 | 镜像化从第一天做，避免以后无法上 K8s |
| Flutter 现在就锁 | 等 SDK POC 再选端，等于 App 架构永远开不了工 | 若某家 SDK 无法桥接 Flutter，换 SDK，不换 App 框架 |

**唯一允许的局部推翻**：量体 SDK 若在 Flutter 上完全无法封装，优先换供应商；只有两家都无法封装时，才重开「App 是否改原生」评审。在此之前 Flutter 视为已定。

## 4. 仓库与目录（核心架构的物理形态）

代码不进 Xingcai 小说仓。新产品独立仓 `FitMe/`（与 `/root/Xingcai` 并列）。文档现阶段仍在 Xingcai 的 `智能量体试衣/`，迁仓时整包进入 `FitMe/docs/`。

```
FitMe/
├── README.md
├── docs/                      # 产品 + 技术文档（迁入后）
├── contract/                  # 唯一真源
│   ├── openapi.yaml           # C 端 + 后台 REST
│   ├── proto/                 # measure / ocr / render
│   ├── errors.yaml            # 错误码
│   └── events.yaml            # 埋点字典
├── apps/                      # Flutter App（骨架期可后建，接口先定）
├── web/                       # React 后台
├── services/
│   ├── server/                # Go 模块化单体 + worker
│   └── algo/                  # FastAPI + gRPC：measure / ocr
├── infra/
│   ├── docker-compose.yml     # postgres / redis / server / algo / admin
│   └── migrate/               # 亦可放在 server/migrations
└── Makefile                   # make up / test / lint / gen-api
```

### Go 单体内部（这是「核心架构」本体）

```
services/server/
├── cmd/
│   ├── api/                   # C 端 + 后台 HTTP 入口（路由前缀隔离）
│   └── worker/                # 异步任务
├── internal/
│   ├── identity/
│   ├── body/
│   ├── catalog/
│   ├── recommend/
│   ├── feedback/
│   ├── config/
│   ├── admin/
│   ├── audit/
│   └── shared/                # 加密、鉴权中间件、分页、错误码
│       ├── crypto/            # 围度字段加解密，业务模块禁止自己 AES
│       ├── auth/
│       └── module.go          # 模块间只依赖接口
├── migrations/
└── configs/
```

每个业务模块统一四层：`api`（HTTP）→ `service` → `repo`；**其它模块只能 import 对方的 service 接口，禁止 import repo 和表结构。**

第一期 **必须建好、但实现可以是空/手动** 的接口：

```go
// 量体：第一期只接 ManualProvider
type MeasureProvider interface {
    Measure(ctx context.Context, req MeasureRequest) (MeasureResult, error)
}

// 商品来源：第一期只接 ManualSource
type ProductSource interface {
    Parse(ctx context.Context, raw string) (ProductDraft, error)
}
```

业务代码禁止直接出现厂商 SDK import。这是架构能否「先搭起来、以后还能换」的分界线。

## 5. 运行时拓扑（骨架期）

```
浏览器(后台) ──┐
              ├──► server:8080  /api/v1     （C 端，公网将来）
curl/App ─────┤         :8080  /admin/v1   （后台，内网）
              └──►        │
                          ├── PostgreSQL :5432
                          ├── Redis :6379
                          └── gRPC algo :9090
                                └── MeasureProvider.Manual   ← 第一期唯一实现
                                └── OcrProvider.Stub         ← 返回「请手填」
```

骨架验收（技术人员 clone 后一天内必须能做到）：

1. `docker compose up` 后 `GET /healthz` 返回 ok  
2. 迁移自动跑完，核心表存在  
3. 注册/登录拿到 token  
4. 创建手动身体档案（胸腰臀明文进接口、库内密文）  
5. 手填尺码表 → `POST /recommend/size` 返回推荐码和部位诊断  

这五步不过，不算核心架构搭起来。

## 6. 核心架构要先立住的 8 条纪律

技术人员熟悉项目，先记这 8 条，比记框架名更重要：

1. **推荐引擎是规则，不是模型。** 松量区间在 `cfg_ease_rules`，改规则不发版。  
2. **全系统共用一份围度字段字典**（《02》附录 A）。厂商字段、尺码表表头、接口 JSON 都归一到 `chest` / `waist` 这一套 key。  
3. **平铺胸围必须判定口径。** 45–70 当半宽 ×2；存疑则该部位不参与推荐。  
4. **推荐记录打快照**：身体版本 + 尺码表版本 + 规则版本，事后可复现。  
5. **敏感数据**：围度加密、照片（后期）直传短存、同意记录、审计只追加。日志里不许出现围度数字。  
6. **模块不互探表。**  
7. **外设可替换。** Measure / ProductSource / OCR 三套接口，第一期全部手动/桩实现。  
8. **接口先于页面。** 改 API 先改 `contract/openapi.yaml`，再 `make gen-api`，禁止端上手写字段。

## 7. 技术路线下的开工批次（架构搭建）

只排「把骨架立住」所需批次，功能堆砌见 PRD 第七章。

| 批次 | 产出 | 完成定义 |
| --- | --- | --- |
| A. 仓与工具链 | 仓库、Compose、Makefile、lint、migrate、OpenAPI 空壳 | 新人按 README 能起环境 |
| B. 身份与合规底座 | `identity` + `audit` + 字段加密 + consent | 无 consent 不能写身体数据 |
| C. 配置中心 | 品类模板 + 松量规则 + Feature Flag 表与后台编辑（可先 SQL 种子数据） | 改规则不改 Go 代码即可变推荐 |
| D. 选码内核 | `body` 手动档案 + `catalog` 手填尺码表 + `recommend` 规则引擎 | 切片五步验收通过 |
| E. 后台最小壳 | 登录、规则查看/编辑、尺码表录入 | 运营能配三类品类（T恤/衬衫/裤装） |
| F. 算法进程桩 | `algo` 起来，gRPC 通，ManualProvider 可调 | 换 SDK 时只加一个 adapter 文件 |
| G. App 最小壳 | Flutter 登录 + 手填 + 展示推荐文字 | 不接相机、不接 3D |

**A→D 是核心架构；E→G 是挂上去的端。** 不要在 A 没完成时并行写 3D 或淘宝解析。

批次 D 的推荐引擎按《04》的规则公式实现最小集：部位评分 + 肩宽/腰围硬约束 + 置信度。不接品牌偏差、不接协同过滤。

## 8. 技术人员怎么用这份路线熟悉项目

建议顺序（约 1～2 天）：

1. 读本文第 2、4、6 节（栈、目录、纪律）  
2. 读《产品需求文档》第零章 + 第七章（做什么、不做什么）  
3. 背《02》附录 A 字段字典（全员通用语言）  
4. 读《01》第 3～4 章（模块职责）  
5. 本地 `compose up`，用 curl 走完第 5 节五步验收  
6. 对照《04》第 3 章看 `recommend` 代码  

不要求第一周读完 9 份文档。先能改松量规则并看到推荐结果变化，就算入门。
