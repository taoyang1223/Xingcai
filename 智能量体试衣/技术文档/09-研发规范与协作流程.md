# 09 · 研发规范与协作流程

> 背景：三端（iOS/Android/Web 后台）+ 服务端 + 算法同期开发，协作成本是最大的隐性损耗。本文档的目标是把"靠默契"变成"靠规则"。
> 关联：《03-API接口设计规范》第 5 章契约管理、《07-部署运维》第 3 章 CI/CD

---

## 1. 仓库结构

起步采用 **monorepo**（与 Xingcai 小说仓分离的独立 `FitMe/` 仓）。契约仍是唯一真源，但放在仓内 `contract/`，不先拆 6 个 Git 仓。目录与锁栈见《00 技术路线》第 4 节。

端成熟、发布节奏明显分叉后，再按目录拆仓：

```
FitMe/                  # 现阶段唯一代码仓
├── contract/           # OpenAPI、protobuf、错误码、埋点字典
├── apps/                  # Flutter App
├── web/                   # React 后台
├── services/server     # Go 模块化单体
├── services/algo       # Python
└── infra/              # Compose；日后 K8s
```

接口变更必须先改 `contract/` 再生成各端代码，禁止手写 DTO。这和「多仓时契约独立」是同一条纪律，只是物理上先同仓。

## 2. 分支模型与提交

### 分支

```
main        主干：当前就是 FitMe 架构代码。骨架期允许直接推送到 main
develop     集成分支（团队小可省略，直接 main + feature）
feature/*   功能分支，命名 feature/{需求号}-{简述}
fix/*       缺陷修复
hotfix/*    线上紧急修复，从 main 拉，修完回合 main 与 develop
release/*   发布分支（App 需要，服务端可不用）
```

**主分支约定（已按本仓现状修订）**：

- 本仓 `main` 的内容以 FitMe 程序骨架为准，不是旧小说仓历史。
- **骨架落地 / 与远程无关历史对齐**：允许把本地架构提交推上 `main`（含 `--force-with-lease` 覆盖旧 `main`）。只覆盖确认过的旧尖端，禁止无 lease 的 `--force`。
- **骨架稳定之后**：日常功能走 `feature/*` + PR 合入 `main`，不再用强推当常规发版手段。
- 日常仍禁止强推别人正在用的功能分支。

分支存活时间 **不超过 5 天**。超过说明任务拆得太大，应当拆分——长分支必然带来痛苦的合并冲突。

### 提交信息（Conventional Commits）

```
<type>(<scope>): <subject>

feat(recommend): 增加品牌偏差修正逻辑
fix(catalog): 修复平铺尺码表未乘2的问题
refactor(body): 抽取 MeasureProvider 接口
docs(api): 补充建模任务接口示例
```

type 取值：`feat` `fix` `refactor` `perf` `test` `docs` `chore` `build`。提交信息用中文写清楚"改了什么"，不写"修改一下"这类无信息量的内容。

## 3. Code Review

### 规则

- 所有代码经 PR 合入，**至少 1 人 Review**；涉及安全、合规、算法核心、数据库变更的，**必须 2 人且其中 1 人为该域 Owner**。
- PR 描述模板：改动内容、关联需求、测试情况、是否影响接口、是否需要配置/数据变更、回滚方式。
- 单个 PR 建议 <400 行改动。超大 PR 的 Review 质量必然低，等于没 Review。
- 24 小时内响应，不要让 PR 挂着阻塞他人。

### Review 必查清单（本项目特有）

```
□ 是否有身体数据、手机号进入日志？
□ 敏感字段是否走了加密存取封装？
□ 是否校验了资源归属（防 IDOR）？
□ 是否绕过了 consent 校验？
□ 是否跨模块直接访问了别人的表（破坏模块化单体边界）？
□ 是否在业务代码里直接调用了厂商 SDK（破坏 MeasureProvider 防腐层）？
□ 新增的规则/阈值是否写死在代码里（应进配置中心）？
□ 第三方调用是否有超时、重试上限与降级？
□ 接口变更是否同步更新了契约仓库？
```

前六条是**架构与合规红线**，发现即打回，不接受"下个迭代再改"。

## 4. 编码规范

| 端 | 规范 | 工具 |
| --- | --- | --- |
| Go | Uber Go Style Guide | golangci-lint、gofumpt |
| Python | PEP8 + 类型标注 | ruff、mypy、black |
| Dart | Effective Dart | dart analyze、dart format |
| TypeScript | Airbnb 变体 | ESLint、Prettier、tsc strict |
| SQL | 见《02-数据库设计》第 1 章 | sqlfluff |

统一约束：

- **禁止魔法数字**。所有阈值（松量、置信度门槛、限流值）进配置或常量，并注释来源。
- **错误必须处理**，不允许吞异常；错误信息要带上下文，便于定位。
- **注释写为什么，不写做什么**。特别是算法部分的经验系数，必须注明依据（"该系数来自 200 人标定集拟合，见评测报告 v3"）。
- 公共函数必须有单测；修 Bug 必须补一条能复现该 Bug 的用例。

## 5. 需求到上线的流转

```
需求提出（产品）
  → 需求评审（产品+技术+设计+测试，明确验收标准与埋点）
  → 技术方案设计（复杂需求必须先出方案文档并评审）
  → 契约先行（先定 API，三端并行开发）
  → 开发 + 自测
  → 提测（附自测报告与影响范围）
  → 测试（含回归与算法黄金集）
  → 验收（产品按验收标准逐条确认）
  → 发布评审（走《07 文档》上线清单）
  → 灰度 → 全量
  → 上线复盘（指标是否达到预期）
```

**"契约先行"是三端并行的关键。** 需求评审后 1–2 天内必须定下接口，各端基于 Mock 并行开发，否则客户端会一直在等后端。

### 技术方案文档的触发条件

满足任一即需先写方案并评审：涉及 3 个以上模块、引入新的中间件或第三方服务、变更核心数据结构、影响推荐结果、涉及敏感数据处理方式变更。

方案文档格式固定：背景与目标、可选方案对比、选定方案与理由、影响面、风险与回滚、工作量拆分。评审通过后把"选定方案与理由"补一条 ADR 进《01-技术架构设计》第 10 章。

## 6. 环境与配置纪律

- 新增配置项必须四套环境同步添加，缺一即视为未完成。
- 配置变更走审批（尤其是松量规则与 Feature Flag），生产配置变更同样要留痕。
- **严禁在代码中出现环境判断**（`if env == 'prod'`）来改变业务逻辑。差异一律通过配置表达，否则测试环境验证的就不是真实逻辑。
- 密钥只存密钥管理服务，本地开发用专用的测试密钥。

## 7. 文档维护

| 文档 | Owner | 更新时机 |
| --- | --- | --- |
| 产品需求文档 | 产品 | 需求变更时 |
| 01 技术架构 | 架构/后端负责人 | 架构决策变更时，同步追加 ADR |
| 02 数据库设计 | 后端负责人 | **每次表结构变更必须同步**，随迁移脚本一起提交 |
| 03 API 规范 | 后端 + 契约仓库 | 接口变更即更新（由 OpenAPI 自动生成部分内容） |
| 04 算法设计 | 算法负责人 | 规则或模型调整时 |
| 05 客户端架构 | 客户端负责人 | 技术选型或分层变更时 |
| 06 安全合规 | 安全 + 法务 | 法规或处理方式变更时 |
| 07 部署运维 | 运维 | 架构或流程变更时 |
| 08 测试策略 | 测试负责人 | 评测体系变更时 |
| 09 本文档 | 技术负责人 | 流程变更时 |

**文档随代码走**：改了表结构却没改文档的 PR，Review 时应当打回。文档滞后三个月后就没人信了，也就没人看了，这套文档的投入就白费了。

## 8. 术语一致性（三端 + 产品 + 算法必须统一）

| 统一用词 | 禁止的混用 | 说明 |
| --- | --- | --- |
| 净体尺寸 | 人体尺寸、实际尺寸 | 指人体本身 |
| 成衣尺寸 | 衣服尺寸、商品尺寸 | 指衣服 |
| 松量 | 余量、宽松度、ease | 成衣 − 净体 |
| 身体档案 | 人体模型、身材档案 | 数据实体名 `body_profile` |
| 3D 模型 | 人体模型、虚拟形象 | 指网格资源 |
| 围度 | 尺寸、维度 | 特指周长类测量值 |
| 平铺量 / 围量 | 半围、全围 | 口径，见《02》附录 A |
| 推荐码 | 建议尺码、最佳尺码 | 引擎输出 |

代码标识符、数据库字段、接口字段、UI 文案、日志，**五处用词必须一致**。这看起来是小事，但在跨端团队里，"尺寸"到底指人还是指衣服这种歧义，会实实在在地造成线上 Bug。

## 9. 团队分工与协作节奏

### 最小团队配置（对应 PRD 开放问题 7）

| 角色 | 人数 | 主要交付 |
| --- | --- | --- |
| 技术负责人 | 1 | 架构、技术决策、评审 |
| 后端 | 2–3 | 业务服务、后台 API、任务调度 |
| 算法 | 1–2 | 量体适配与评测、OCR、推荐引擎 |
| 客户端 | 2–3 | Flutter + iOS/Android 原生（3D 与相机） |
| 前端 | 1–2 | Web 后台 |
| 测试 | 1 | 自动化 + 算法评测 + 真机 |
| 运维/SRE | 0.5–1 | 可与后端兼任，但 GPU 与合规巡检必须有人负责 |
| 产品 | 1 | 需求、指标、验收 |
| 设计 | 1 | App 设计 + 拍摄引导（**这块设计质量直接影响建模成功率**） |
| 运营/审核 | 1–2 | 尺码表审核、规则维护、内测运营 |

### 节奏

- 两周一个迭代；迭代计划会、每日站会（≤15 分钟）、迭代评审与回顾。
- **周三为接口冻结日**：当周迭代的接口变更需在周三前完成，之后只修不加，给客户端留联调时间。
- 每两周一次技术分享（轮流），重点同步算法侧进展——算法与工程之间的信息差是这类项目最常见的返工来源。

## 10. 新人上手路径

建议按顺序读：

1. 《产品需求文档》第零、一、七章 —— 搞清楚在做什么、MVP 边界在哪
2. 《01 技术架构设计》 —— 整体结构与四条硬约束
3. 《02 数据库设计》附录 A —— **先背字段字典**，这是全系统的通用语言
4. 本域的详细文档（04/05/06 之一）
5. 《09 本文档》第 3、8 章 —— Review 清单与术语表

上手第一周建议做的事：跑通本地环境、完整走一遍 E1 链路（注册到建模）、用软尺给自己量一次并与系统输出对比。**亲自体验一次建模误差，比看十页文档更能理解这个产品的难点。**
