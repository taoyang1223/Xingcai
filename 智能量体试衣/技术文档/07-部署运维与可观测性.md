# 07 · 部署运维与可观测性

> 范围：环境规划、CI/CD、发布策略、监控告警、容灾备份、成本控制、值班响应
> 关联：《01-技术架构设计》、《06-安全与合规设计》第 5.3 节生产访问控制

---

## 1. 环境规划

| 环境 | 用途 | 数据 | 访问 |
| --- | --- | --- | --- |
| `dev` | 开发自测 | 合成数据 | 开发全员 |
| `test` | 集成测试、自动化回归 | 合成数据 | 开发 + 测试 |
| `staging` | 预发，配置与生产一致 | **脱敏合成数据，严禁同步生产数据** | 测试 + 少数研发 |
| `prod` | 生产 | 真实数据 | 严格受限，需审批 |

四套环境的**配置项完全同名**，仅取值不同，避免"测试环境好好的，上线就炸"。配置走配置中心 + 环境变量，密钥走密钥管理服务，**代码仓库中零密钥**。

## 2. 部署架构

### 2.1 MVP 阶段（务实优先）

```
                    CDN（静态资源、模型文件）
                          │
                  ┌───────▼────────┐
                  │  负载均衡 SLB   │
                  └───┬────────┬───┘
             公网入口 │        │ 内网入口（后台，仅 VPN）
                  ┌───▼────┐ ┌─▼──────────┐
                  │ 网关    │ │ 网关(admin)│
                  └───┬────┘ └─┬──────────┘
                      │        │
              ┌───────▼────────▼────────┐
              │  K8s 集群                │
              │  ┌────────────────────┐ │
              │  │ app-api (2~6 副本) │ │  业务单体
              │  │ admin-api (2 副本) │ │
              │  │ worker (2~4 副本)  │ │  异步任务
              │  │ measure-svc (GPU)  │ │  按需扩缩，可为 0
              │  │ ocr-svc (2 副本)   │ │
              │  │ render-svc (GPU)   │ │
              │  └────────────────────┘ │
              └──────┬──────────────────┘
                     │
    ┌────────────────┼─────────────────┬──────────────┐
    ▼                ▼                 ▼              ▼
PostgreSQL       Redis 集群        RocketMQ         OSS
(主 + 只读从)     (哨兵)                          (两个桶)
```

**GPU 节点用独立节点池**，配 HPA 与定时缩容（凌晨调用量极低时缩到 0 或 1），这是成本大头。

### 2.2 资源配置起点

| 服务 | 副本 | 规格 | 扩缩依据 |
| --- | --- | --- | --- |
| app-api | 2→6 | 2C4G | CPU 60% / QPS |
| admin-api | 2 | 2C4G | 固定（内部用户少） |
| worker | 2→4 | 2C4G | MQ 积压长度 |
| measure-svc | 0→3 | GPU T4 | 任务队列长度 |
| ocr-svc | 2→4 | 4C8G | 队列长度 |
| PostgreSQL | 1主1从 | 4C16G / 500G SSD | 手动升配 |
| Redis | 3 节点 | 4G | — |

> 按《01-技术架构设计》第 8 章的容量估算，MVP 阶段并发压力很小。**不要一上来搞多可用区多活**，把钱花在 GPU 和数据安全上更划算。

## 3. CI/CD

### 3.1 流水线

```
Push / PR
  ├─ 静态检查：lint、格式化、架构边界检查（禁止跨模块越界 import）
  ├─ 单元测试（覆盖率门槛：核心算法 ≥80%，整体 ≥60%）
  ├─ Secret 扫描（gitleaks）+ 依赖漏洞扫描（SCA）
  ├─ 契约校验：OpenAPI 破坏性变更检测
  └─ 构建镜像 → 推送仓库（镜像带 git sha 标签）
        ↓ 合入 main
  ├─ 部署 test → 自动化集成测试 + 算法黄金集回归
        ↓ 人工确认
  ├─ 部署 staging → 冒烟 + 性能基线
        ↓ 发布审批
  └─ 部署 prod（金丝雀 → 灰度 → 全量）
```

**算法黄金集回归是必须卡在流水线里的**（见文档 04 第 5.1 节）：量体精度、OCR 准确率、推荐一致率任一指标跌破阈值，直接阻断发布。否则算法质量会在无人察觉中缓慢退化。

### 3.2 服务端发布策略

金丝雀 1 个副本 → 观察 10 分钟核心指标（错误率、P95 延迟、推荐成功率）→ 逐步放量 25%/50%/100%。数据库变更与代码发布**分离**，遵循「先加列 → 双写 → 迁移 → 切读 → 删旧列」，任何一步都可独立回滚。**禁止在发布窗口做不可逆的 DDL。**

### 3.3 App 发布策略

App 的回滚成本远高于服务端，纪律要更严：

- 版本号 `主.次.修订`，构建号自增。
- 灰度：Android 用应用商店分阶段发布（5%→20%→50%→100%），iOS 用 TestFlight + 分阶段发布。
- **服务端必须兼容旧版 App 至少 2 个大版本**，新功能用 Feature Flag 控制，出问题服务端关开关即可止血，不必等应用商店审核。
- 强更策略：只在安全问题或协议不兼容时使用，通过 `/common/config` 下发。

## 4. 可观测性

### 4.1 三支柱

| 支柱 | 工具 | 要点 |
| --- | --- | --- |
| 指标 Metrics | Prometheus + Grafana | 业务指标与技术指标同一看板，方便关联分析 |
| 日志 Logs | Loki / ELK | 结构化 JSON，**必带 trace_id**，敏感字段自动脱敏 |
| 链路 Traces | OpenTelemetry + Jaeger | 覆盖网关→业务→算法→第三方全链路 |
| 异常 | Sentry | 客户端崩溃 + 服务端异常，按版本聚合 |

### 4.2 日志脱敏（硬性要求）

日志框架内置脱敏中间件，对 `chest/waist/hip/phone/photo_key` 等字段自动替换为 `***`。**围度数值绝对不允许出现在日志中**——日志系统的访问控制通常比数据库宽松得多，这是最容易被忽视的泄露通道。

### 4.3 核心监控看板

**技术看板**

| 指标 | 告警阈值 |
| --- | --- |
| 接口错误率 | >1% 持续 5 分钟 |
| P95 延迟 | 推荐 >800ms / 解析 >5s |
| 建模任务失败率 | >5% |
| 建模任务队列积压 | >100 或等待 >3 分钟 |
| 第三方 SDK 错误率 | >5%（触发自动熔断切换） |
| 数据库连接池使用率 | >80% |
| GPU 利用率 | 持续 >90% 或持续 <10%（后者是浪费钱的信号） |

**业务看板**（产品与运营每天看）

建模完成率、推荐采纳率、解析成功率、无法推荐率、用户校正率、各供应商精度对比、当日 SDK 成本。

**合规看板**（每天自动巡检）

| 检查项 | 告警级别 |
| --- | --- |
| 存在 `finished_at` 超 1 小时但 `photo_purged_at` 为空的任务 | **P0** |
| raw-photo 桶中存在超 1 小时的对象 | **P0** |
| 无 consent_id 的建模请求 | **P0** |
| 身体数据明文查看次数异常（>日均 3 倍） | P1 |
| 审计日志写入中断 | P1 |

> 合规看板不是可选项。前两条任一触发，都说明删图机制失效，属于随时可能演变成数据泄露事故的状态，必须当作 P0 处理。

### 4.4 告警分级与响应

| 级别 | 定义 | 响应时间 | 通知方式 |
| --- | --- | --- | --- |
| P0 | 服务不可用、数据泄露风险、资金损失 | 15 分钟 | 电话 + 群 |
| P1 | 核心功能降级、关键指标异常 | 1 小时 | 群 + 短信 |
| P2 | 非核心异常 | 当日 | 群 |
| P3 | 优化建议 | 迭代内 | 工单 |

告警必须可执行：每条告警配一条 Runbook 链接，写明"这个告警意味着什么、先查什么、怎么临时止血"。**没有 Runbook 的告警等于噪音**，最终会被静音。

## 5. 备份与容灾

| 对象 | 备份 | RPO | RTO |
| --- | --- | --- | --- |
| PostgreSQL | 每日全量 + WAL 连续归档，异地保留 7 天 | ≤5 分钟 | ≤1 小时 |
| OSS 模型资产 | 跨区域复制 | ≤15 分钟 | ≤30 分钟 |
| Redis | 缓存可重建，不做强备份 | — | — |
| 审计日志 | 每日归档至冷存储，保留 3 年，WORM 只读 | ≤1 天 | ≤4 小时 |
| 配置 | Git 版本化 | 0 | 分钟级 |

**每季度做一次恢复演练**，并在演练中顺带执行注销用户的备份清除（见文档 06 第 6 节）。没演练过的备份约等于没有备份。

降级预案：

| 故障 | 降级动作 |
| --- | --- |
| 量体 SDK 全挂 | 关闭拍照建模入口，引导手动建档，首页公告 |
| OCR 服务挂 | 商品解析降级为"请手动录入尺码表" |
| 渲染服务挂 | 隐藏 3D 试穿，保留文字版部位诊断（**核心价值仍在**） |
| 主库故障 | 切只读从库，产品进入只读模式（可查历史，不可建模） |
| MQ 积压 | 暂停新建模任务受理，前端排队提示 |

> 注意降级的优先级排序：3D 试穿是锦上添花，**部位诊断文字才是核心价值**。挂了渲染不该影响主功能，架构上要保证这一点。

## 6. 成本控制

MVP 阶段成本大头排序：**第三方 SDK 调用费 > GPU > 带宽/存储 > 数据库**。

| 措施 | 说明 |
| --- | --- |
| SDK 成本日报 | 按供应商统计当日调用量与费用，超预算自动降级 |
| 建模次数限制 | 单用户 5 次/小时、20 次/天（同时是防刷手段） |
| GPU 定时缩容 | 夜间缩到 0；用队列触发扩容，冷启动延迟可接受（任务本身就是异步的） |
| 缓存命中率 | 商品解析缓存目标 ≥60%，直接省下 OCR 与解析成本 |
| CDN | 模型文件与图片走 CDN，回源率 <10% |
| 存储生命周期 | 原图 1 小时、日志 30 天转冷存储 |

每月出一次成本复盘，重点看**单个活跃用户的边际成本**。如果这个数字降不下来，商业模式不成立——这比任何技术指标都重要。

## 7. 值班与事故管理

- **工作日轮值 + 非工作时间 oncall**，一线响应人 + 后备升级人。
- 事故分级同告警分级；P0/P1 必须写复盘文档（背景、时间线、根因、影响面、改进项、Owner、截止日）。
- 复盘**对事不对人**，改进项进入迭代排期并跟踪关闭。
- 每月统计 MTTD（平均发现时间）与 MTTR（平均恢复时间），持续下降为目标。

## 8. 上线检查清单（Go-Live Checklist）

发布前逐项确认，任何一项不过不予发布：

```
□ 所有 P0/P1 缺陷已关闭
□ 算法黄金集回归通过（量体精度、OCR、推荐一致率）
□ 性能压测达标（见文档 08）
□ 安全扫描无高危项，渗透测试报告已闭环
□ 合规清单完成（PIA、隐私政策、SDK 清单、备案）
□ 合规巡检任务已部署并验证告警可达
□ 监控看板与告警规则已配置，Runbook 齐全
□ 数据库变更脚本已在 staging 验证，回滚脚本就绪
□ 降级开关已验证（逐个关掉第三方依赖试一遍）
□ 备份已验证可恢复
□ 客服话术与 FAQ 就绪
□ 灰度方案与回滚方案已评审，回滚负责人已指定
```
