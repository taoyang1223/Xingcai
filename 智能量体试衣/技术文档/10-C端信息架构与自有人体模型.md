### 已记录的产品口径（本节是索引，正文见对应小节）

0. **主难题：让客户方便且精准地建起体型模型。** 解法：对准框拍摄 + 参数人台 + 穿着养精度，不要填表或扫描舱。（§1 / §1.2）
1. 登录可以像微信/支付宝，但**不用真名、不采身份证**；首页只干「粘贴链接看码」。（§3.1）
2. 三个围度只是摘要；档案是字典 22 项，按品类吃子集。（§4）
3. 客户只有手机、没有软尺、常常一个人：主路径是拍照，不是填表。（§4.2）
4. 穿贴身家居/运动装拍；禁止裸体。（§4.3）
5. 衣服会挡，但不靠外轮廓量：肩宽看肩峰，肚子看侧面+体重；卫衣直接拦。（§4.4）
6. 采了不等于留着：原图短删、糊脸、围度加密、训练默认用合成图。（§4.5 →《06》）
7. 自有 \(M(\beta)\) 的目的之一就是解决「方便且精准建档」；SDK 只当教师。（§1 / §5）
8. **后续一切开发必须保护客户隐私、遵守相关法律；与功能冲突时停功能。**（《06》《09》第 0 节、`.cursor/rules/privacy-legal.mdc`）

## 1. 一句话与主难题

登录可以做成微信 / 支付宝那种一键授权；进来之后每天只回答一件事：**这件衣服，我穿哪个码。**  
精准档案不是三个围度数字，而是自有参数化人体 \(M(\beta)\)：简易操作 + AI 反解参数，3D 人台和 22 项围度从同一组 \(\beta\) 长出来。

**真正难的不是登录，也不是合规条文，而是：客户只有一部手机，没有软尺，常常就一个人，还不愿脱衣服——却要把体型模型建准。** 方便和精准默认打架。

**自有数学模型 \(M(\beta)\) 的目的之一，就是专门解决这个矛盾：** 客户只提供很少、很便宜的观察（身高 + 正侧两张贴身照），模型负责补全成自洽的 22 项和 3D 人台。没有这套模型，方便就只能填表或猜三围，精准就只能上扫描舱。拍摄引导和穿着反馈是入口与闭环，**把两张便拍照变成准档案的，是人台数学，不是更多表单。**

### 1.1 方便 × 精准：不能拆开卖

| 只要方便会变成 | 只要精准会变成 | 我们要的 |
| --- | --- | --- |
| 填 22 个框 / 只填身高体重就说「已建档」 | 进扫描舱、裸体、找人帮忙按快门 | 靠墙倒计时拍正侧两张，贴身家居/运动装 |
| 卫衣也给一个码 | 不合格照片也硬出高置信度 | 端侧拦住废片；松衣请换；没有侧面不报准腰腹 |
| 好看的 3D 雕塑 | 数字准、人台对不上 | 同一组 \(\beta\) 长出网格和 22 项，自洽误差 ≈ 0 |
| 把照片留下来反复抠 | 要真名身份证才放心建模 | 照片当燃料用完即删；账号伪匿名 |

验收也必须两头一起过（见第 6 节）：端到端 ≤ 15 秒 **且** 胸腰臀 MAE ≤ 2cm、人台与数字自洽。只过一边，建档功能不算做成。

产品判断口诀：**客户侧步骤再减，不能减侧面、不能减贴身、不能把拦截改成「凑合算」；精度再加，不能加软尺、不能加第二部设备、不能加裸体。** 精度缺口用滑杆和「这件偏紧/偏松」补，不把难度甩回客户填表。

### 1.2 推荐解法：一次拍准骨架，用穿着把精度养上来

不要找「又完全不费事、又一次实验室级」的神操作，那种不存在。好的解法是把难度从客户身上挪到三层系统里。

**第一层：把拍摄做成对准游戏，而不是自拍。**  
屏幕上叠一个半透明无头人台框。客户把手机靠墙，走进去，肢体和框对齐，端侧判定合格就自动拍，人不用按快门。正面过了，框转成侧面剪影，原地转 90° 再自动拍。这比「请保持 A 字站」管用：距离、站姿、是否拍全，在快门前就锁死。废片不上云。贴身短袖/运动装用图示，不是用「请少穿衣服」。

**第二层：两张照只反解人台参数，不在衣服外皮上量。**  
身高钉尺度；正面钉肩宽和左右宽；侧面钉腹厚；体重只是肚子的先验，可填可不填。22 项从 \(M(\beta)\) 上切出来，数字和 3D 同一份。卫衣、缺侧面、没站进框：拦截或标成弱档，禁止假装很准。这是精准的来源，不是多要客户填几个数。

**第三层：模型是活的，第一次只要求「能推荐」，不是「能量体师」。**  
拍完立刻给人台，只留两个不像就拖的杆：**肚子、肩宽**。其余围度跟着 \(\beta\) 走。之后每推荐一件问「偏紧 / 刚好 / 偏松」，把偏差写回模型。三次穿着反馈，腰腹会比再拍十张卫衣照更准。方便的是客户永远不填厘米；精准是在使用里长出来的。

客户从打开到可用档案，目标动作只有：填身高 → 靠墙对准拍两次 → 看人台像不像。中间没有尺、没有第二个人、没有裸体。隐私仍按 4.5：照片燃料、档案只留 \(\beta\)。

**明确不选的「看起来更酷」方案：** 转圈拍视频当主路径（流量大、糊脸难、合格率不比两张静帧高）；LiDAR 当全员方案（机型少）；相册里随便挑一张生活照（姿势和衣服都不可控）。这些可以以后做增强，不能替换第一层。

## 3. C 端信息架构

底栏只四个坑，不要商城、社区、消息。

| Tab | 职责 |
| --- | --- |
| 首页 | 人台状态 + 唯一主操作（粘贴商品链接看码）+ 最近推荐 |
| 试穿 | 3D 人台穿衣（后期） |
| 档案 | 22 项围度、完整度、校正、拍照补测 |
| 我的 | 授权、隐私、退出 |

### 3.1 登录：一键授权，匿名账号

做成微信 / 支付宝那种「品牌 + 一键授权」即可。登录只解决「这是同一个人」，不解决体型，**也不解决现实身份**。

**C 端禁止采集、禁止入库、禁止在注册页出现的字段：**

| 禁止 | 原因 |
| --- | --- |
| 真实姓名 / 请输入姓名 | 选码不需要法定姓名；和身体数据绑在一起，泄露后可直接对上人 |
| 身份证号、证件照、人脸核身、银行卡实名 | 本产品不是支付机构也不是运营商，无法律依据采集 |
| 微信/支付宝的实名资料、通讯录 | 授权只拿 `openid` / `unionid`（及可选手机号），不拉实名 |

账号怎么建：

- 微信或手机号验证码登录。手机号若采集，只作登录与找回，HMAC 查找 + 密文存储，界面不展示完整号码。
- 展示名由系统生成（如「用户 7F2A」），允许用户改成任意昵称，**文案不得写成「真实姓名」**，也不做实名校验。
- 体型模板（女/男/中性）只服务人台，不是证件性别，不和身份证比对。
- 后台 `adm_users.real_name` 是员工花名册，与 C 端用户表隔离，禁止把客户真名字段抄到 `users`。

远期定制寄送若需要收件人，另建履约地址簿，和身体档案分表、分权限、单独同意；**注册登录阶段一律不收。**

未同意 `body_photo` / 身体数据处理时，不能写拍照档案；不同意拍照必须仍能用身高体重走弱档（见 4.2）。厘米数手填不是登录后的默认路径。

### 3.2 首页：不是电商首页，也不是工具箱

只放四层：

1. **人台状态**：无头人台 + 完整度（如「18/22 已测 · 推荐可用」）。不要把胸腰臀三个数画成「整份档案」。
2. **唯一主操作**：「粘贴淘宝链接，看穿哪个码」。手填尺码表是辅助，不和主按钮抢。
3. **最近推荐**：上次结果 + 一句风险（如袖长可能偏短），避免每天从零开始。
4. **隐私条**：长期挂在底部——「人体照片处理完即删，不留原图」。登录授权页说过一次不够。

空态与日常态必须分开：未建档时粘贴链接禁用，主按钮是「拍照建档」（一个人靠墙拍）。不愿拍的走「用身高体重先建弱档」。厘米数手填只藏在档案页高级校正。建档前给确定推荐会污染信任。

### 3.3 档案页：完整度才是档案

档案页按组展示字典字段，每一行带状态：**高 / 中 / 推算 / 已校正 / 缺失**。  
缺失部位不参与对应品类打分；推算值必须拉低置信度。人台与列表联动：校正一个腰围，网格和其他相关围度一起动。

## 4. 围度：摘要 ≠ 档案

胸围 / 腰围 / 臀围只适合当首页或卡片上的**状态摘要**。只收三围建不出准档案：上衣常栽在肩宽、袖窿、臂长、背长；裤子常栽在立裆、大腿围、内缝。腰臀差大的人只看三围几乎一定推错码。

人体侧以《02》附录 A 为准，共 **22 个可测字段**（单位 cm）：

| 分组 | 字段 |
| --- | --- |
| 骨架（档案元数据，不全是围度） | 身高、体重、性别、年龄段、松紧偏好 |
| 上身围度 | 颈围、胸围、下胸围、腰围、腹围、上臂围、腕围、袖窿围 |
| 上身长度 / 宽度 | 肩宽、背长、背宽、前胸宽、臂长 |
| 下身围度 | 臀围、大腿围、膝围、小腿围、脚踝围 |
| 下身长度 | 立裆深、内缝长、外缝长 |

成衣侧另有衣长、袖长、平铺胸宽等，**只出现在尺码表，不写进人体**。平铺 vs 围量仍按《02》《04》判定，判错会差一倍。

### 4.1 采集分层（不能让用户一次手填 22 项）

| 层 | 做什么 | 置信度 |
| --- | --- | --- |
| 主路径 | 一部手机：靠墙倒计时拍正/侧两张，算法出 22 项 | 按部位给出 |
| 弱档 | 只知道身高体重、不愿拍照：统计体型先用着 | 封顶，首页写明「建议拍照」 |
| 校正 | 不填厘米数：看人台滑杆，或反馈「这件偏紧/偏松」 | 记入已校正 |
| 推荐 | 按品类吃子集，缺的不打分 | 结论写成「仅基于已测部位」 |

衬衫看胸围、肩宽、袖长、衣长；西裤看腰围、臀围、大腿围、立裆、裤长。不敢说「别买」的推荐没有价值（肩宽 / 裤腰硬约束见《04》）。

**禁止把「请填写胸围腰围」当成建档主流程。** 客户只有手机，没有软尺，也量不准。厘米数由模型算，不由用户填。

### 4.2 一部手机、一个人、没有软尺

这是真实使用约束，不是降级场景。设计按这个做：

| 客户做得到的 | 系统替他做的 |
| --- | --- |
| 知道自己大概身高（多数人 ±1～2cm） | 用身高当尺度锚，把照片里的比例变成厘米 |
| 把手机靠墙或立在桌上 | 端侧检测人体入框、距离、竖直、A 字站，合格才自动倒计时拍，人不用按快门 |
| 转个身再拍一张 | 侧面负责腰腹厚度，没有侧面就不敢报精准腰围 |
| 穿较贴身的衣服站直 | 轮廓分割尽量看到衣服下的净体；羽绒服/宽松卫衣直接拦截重拍 |
| 看人台觉得「腰太细了」拖一下 | 滑杆改的是 \(\beta\)，不是让他回忆腰围是 81 还是 84 |

一个人拍全身照的具体做法（不能假设旁边有人帮忙）：

1. 引导「手机靠墙 / 靠杯立在桌上，镜头对着空地」。
2. 语音倒计时，人走开站进框。不合格自动重来，不把废片上传。
3. 正面过了，提示原地转 90°，再倒计时拍侧面。
4. 端侧糊脸后才上传；原图处理完即删。

客户需要敲键盘的，原则上只有 **身高**（体重可填可不填：有则腰腹先验更好，没有也能从轮廓估）。性别用「体型模板：女 / 男 / 中性」，不要做成问卷。年龄段用三档即可。

**不要做的「精准输入」替代品：**

- 让用户拿手机当软尺去量腰（围不起来，误差比照片还大）
- 把 LiDAR / 原深相机当主路径（只有少数 iPhone Pro，Android 碎片化）
- 要求放一张 A4 / 银行卡当比例尺（忘带、拍不清，身高已经能定尺度）
- 空态先甩 22 个输入框

精度不够时，用穿着反馈补，仍不用填数字：推荐一件之后问「偏紧 / 刚好 / 偏松」，把偏差写回 \(\beta\)。这是没有软尺时最接近「实测」的闭环。

不愿拍照的人走弱档：只靠身高体重出统计人台，推荐必须写「仅供参考」，并一直留拍照入口。手填围度只留给极少数愿意对着镜子量的人，藏在档案页「高级校正」，不是首页按钮。

### 4.3 拍照穿什么：贴身衣服，禁止裸体

**产品口径：穿贴身衣服拍。不引导、不要求、不接收裸体或仅内衣照片。**

档案里存的是净体围度（不含衣服），但采集必须在社会可接受的着装下完成。裸体理论上轮廓更干净，转化、合规、应用商店、内容安全四条都会把产品做死。

| 档 | 着装 | 系统行为 |
| --- | --- | --- |
| 推荐拍 | 贴身短袖 / 运动背心 + 紧身裤或薄款打底；口袋掏空、不系宽腰带、长发束起 | 放行，按薄衣厚度做 0.5～1cm 量级的净体修正 |
| 可拍、置信度下调 | 普通 T 恤 + 不太松的长裤 | 放行，腰腹等部位标中等置信度 |
| 拦截重拍 | 羽绒服、大衣、宽松卫衣、连衣裙遮住腰线、裙摆遮住腿形 | 端侧提示换衣，照片不上云 |
| 拒绝 | 裸体、仅内裤/仅文胸、明显色情姿态 | 端侧拦截；已误传的立即删除且不进训练 |

引导文案写成「请换上贴身家居服或运动装」，不要写「尽量少穿衣服」。示例图只用抽象人台或穿运动装的示意，不用真人内衣图。

算法上要同时做两件事：分割出着装轮廓，再估计衣服下的净体 \(\beta\)。合成训练数据必须覆盖「同一个人、同一 \(\beta\)、不同衣服」，否则模型会把卫衣当成体型。推荐引擎吃净体，再和成衣尺码比松量；若把着装围当净体，所有码都会偏大。

女装精度敏感部位（下胸围、腰）靠「运动背心 + 紧身裤」这一档就够，不要为了再抠 1cm 去要内衣照。那 1cm 用滑杆和「这件偏紧」反馈补，比流失和审核风险便宜。

### 4.4 衣服挡住了，肩宽、腰、肚子怎么来

不是在照片上用尺子量衣服外轮廓。两张照只提供约束，真正的肩宽 / 腰围 / 腹围是从 \(M(\beta)\) 上切出来的。衣服越松，约束越弱，该部位置信度越低，直到拦截。

**肩宽（长度，左右肩峰距离）**  
骨骼点，T 恤也挡不住。正面图里左右肩点几乎总能看见。普通短袖下这是最稳的几项之一。会翻车的是落肩卫衣、垫肩外套——肩缝是衣服的不是人的，这类直接拦。

**腰宽 ≠ 腰围**  
正面只能看到左右宽度，那是「腰宽」。档案要的是 **腰围**（一圈的周长）。有肚子的男生，正面常常看不出来：肚子往前挺，左右不一定变宽，T 恤一罩更像个矩形。所以**侧面是刚需**：侧面看到的是腹厚（前后径）。有了正面宽 + 侧面厚，截面近似椭圆（实际由人台网格给出），才有：

\[
\text{腰围} \approx C_{\text{waist}}\bigl(M(\beta)\bigr)
\quad\text{由正面宽、侧面厚、身高尺度共同钉住}
\]

只拍正面、或把宽松衣的外轮廓当腰围，会把所有码推大，有肚子的人误差最大。

**男生肚子被衣服遮住时靠什么**

| 信号 | 作用 |
| --- | --- |
| 侧面轮廓 | 主信号。薄 T 恤会挂在肚子最凸处，侧影仍能看见腹厚 |
| 体重 | 强先验。同样身高，70kg 和 90kg 的腹围统计分布差一截；照片糊了也能把 \(\beta\) 往对的方向拉 |
| 正面腰线有没有凹 | 辅助。有腰窝说明腹不大；没有也不能说明一定有肚子 |
| 人台参数里的腹型维 | \(\beta\) 里单独有腹围 / 腹厚方向，不是把腰围均匀加一圈 |

厚衣服（卫衣、衬衫外扎、羽绒服）侧面也会从胸口垂下来，肚子被布罩住，**侧影是假的**。这时不能「猜一个肚子」还写成高置信度，只能：拦截换衣，或放行但腹围/腰围标成推算，推荐衬衫可以、推荐西裤必须示弱。

**诚实边界**

- 贴身短袖 + 正侧两张：肩宽、腰围、腹围可以过验收线（见第 6 节）。
- 普通 T 恤：肩宽仍可用；腰腹置信度下调，允许用户拖滑杆说「肚子更大」。
- 宽松卫衣 / 外套：不计算，请换衣。算法没有透视，体重先验填不了 10cm 的布料空腔。
- 没有侧面：不准报精准腰围和腹围，最多给低置信弱档。

标定集必须单列「有腹型男性 + 着装」子集。只拿瘦人贴身照报均值，会上线后在目标用户上翻车。

### 4.5 隐私：采了不等于留着

客户怕的不是「拍两张」，是「我的全身照和三围会不会被存下来、被看、被卖」。技术上必须让这句话为真：**照片是一次性燃料，档案只留参数。** 细则以《06 安全与合规设计》为准，C 端口径如下。

| 数据 | 离开手机吗 | 长期留什么 |
| --- | --- | --- |
| 取景画面、姿态是否合格 | 不离开。端侧检测，不合格不上云 | 无 |
| 正/侧两张原图 | 糊脸、剥 EXIF（去 GPS）后，签名直传短存桶，不经业务服务器落盘 | **建模完成即删，桶 1 小时兜底**。业务库不存原图 |
| 人脸 | 默认不要。上传前端侧模糊/裁切。人台无脸 | 无 |
| 22 项围度、\(\beta\)、无头网格 | 加密传输；库内 AES-256-GCM 密文 | 账号存续期；用户可随时删；注销含备份 T+15 清掉 |
| 日志、埋点 | 可离开 | **禁止出现围度数字和照片 URL** |
| 算法训练 | 默认不走用户原图 | 用合成人台图；若要用真实数据必须单独勾 `body_data_train`，可拒且不影响选码 |
| 法定身份 | 不采集 | **不存真实姓名、身份证号、证件照**。账号 = 微信/手机号伪匿名 |

防泄露不靠「我们会保密」一句话，靠五道闸：

1. **少采。** 每次建模就两张，不是相册；不读通讯录、不读位置、不用相册全量权限。
2. **晚出。** 构图、换衣拦截、裸体拦截、糊脸都在手机上做完，废片和脸不出门。
3. **短留。** 原图独立桶、禁止公共读、禁止列举；任务结束删除是流程步骤，失败重试告警，生命周期兜底。
4. **密存。** 拖走数据库也是密文；后台默认脱敏，明文要工单+审批+时限+水印；算法同学只看去标识聚合，不看某个人。
5. **可删。** 撤回拍照同意、删档案、注销，入口和授权一样显眼。分享试穿图必须剥掉围度。

第三方量体若走厂商云，必须单独同意并写清供应商名，合同锁死：不留存、不训练、不出境。优先端侧或照片只在我方短存桶。业务代码不得把原图塞进聊天群、Issue、日志。

首页长期挂「人体照片处理完即删，不留原图」。这不是文案装饰，是和存储生命周期一致的承诺——做不到就不要写。

未成年人：MVP 不提供拍照建档。不满 14 周岁涉及监护人同意，本产品不做。

## 5. 核心技术：自有参数化人体，不是照片雕塑

市场上 Bodygram、3DLOOK、Shaku 做的都是：两张照 → 一堆厘米数 → 一个 avatar。买来的是黑盒：拓扑、标志点、围度口径不在自己手里。换一家，人台变形、推荐漂移。FitMe 后面还要滑杆校正、按品类吃子集、远期给工厂出净体尺寸——必须**同一具人台、同一套测量算子**。

### 5.0 这套数学为什么存在

**第一目的：解决第 1 节的主难题——让客户方便且精准地建档。**

人的身体自由度很高（22 项围度还只是裁缝口径），客户给得起的观察很少（身高、正侧轮廓、可选体重）。\(M(\beta)\) 把身体压到 15～30 维，作用就是：

- **正向**：任意 \(\beta\) → 合法人体网格 → 22 项围度自动齐，数字和 3D 不会打架。
- **反向**：很少的观察 → 求 \(\beta\) → 没拍到的部位由模型按人体统计补全，并打上置信度。
- **校正**：拖一个「肚子」滑杆或「这件偏紧」，只动 \(\beta\) 的几维，其余围度跟着合理变，不用让客户填 22 个数。

所以这不是「先有一个好看的 3D，再往上贴尺子」。**人台数学是建档产品本身。** 拍摄框、糊脸、短删照片，是为了给这个反问题提供干净输入，并满足隐私；渲染只是把 \(M(\beta)\) 画出来。评这套模型成不成，先问：两张贴身便拍照 + 身高，能不能稳定给出可推荐的档案——不是先问网格好不好看。

其余目的（试穿、远期工厂净体）都建立在同一 \(\beta\) 上，不另起一套人体。

### 5.1 模型

固定一具无头、服装友好拓扑的模板 \(M_0\)（不要直接拿学术 SMPL 当生产网格：有商用授权坑，且拓扑是给动画的）。体型用低维参数 \(\beta\)（约 15～30 维）：

\[
M(\beta)=M_0+\sum_i \beta_i B_i
\]

围度不是另存一张表，而是网格上的测量算子 \(C_k(M)\)：在解剖标志点做平面或测地线截面周长，口径对齐国标 / ISO 8559。硬约束：

\[
C\bigl(M(\beta)\bigr)\approx \text{软尺实测}
\]

**档案主键是 \(\beta\)。** 厘米数和 3D 网格都是它的视图。改滑杆或校正一个围度，人台与其余围度一起更新，禁止「数字是 81、模型看起来像 90」。

手填路径是同一套模型的逆问题：已知部分 \(C_k\)，优化 \(\beta\)，缺的部位由模型补，标成推算。

### 5.2 简易操作（用户侧只保留这些）

见 4.2。用户侧不是「填写档案」，而是「靠墙拍两张」。不要 3D 扫描舱，不要用户自己量 22 处。

### 5.3 AI 干什么（不是生成网格）

AI 管反问题，不管「生成一尊独特雕塑」：

1. 检测姿态和关键点，挡住不合格照片（缺脚、侧身当正面、人体太小）
2. 从正 / 侧轮廓估计体型，尽量看到衣服下的净体轮廓
3. 回归 \(\beta\)，用身高把尺度钉死
4. 用 \(C_k\) 算出 22 项围度，并给出部位置信度

照片不进业务库长留。网格不当真相源。NeRF / 高斯溅射好看但量不准，不做产品主路径。

### 5.4 和渲染、推荐的边界

- **人台模型**（本文）：\(\beta\) → 网格 + 围度。核心 IP。
- **原生 3D**：只负责画 \(M(\beta)\)，不另搞一套 Flutter 3D 引擎。
- **推荐引擎**（第一期）：规则吃围度，不吃 \(\beta\)，也不上协同过滤。
- **SDK**：同一接口下的教师或熔断备份，可关掉。

## 6. 核心技术指标

| 指标 | 验收线 |
| --- | --- |
| 胸 / 腰 / 臀 vs 软尺 | MAE ≤ 2.0 cm，P90 ≤ 3.0 cm |
| 肩宽 / 臂长 / 内缝 | MAE ≤ 1.5 cm |
| 模型自洽 | 人台上量出的围度 = 档案数字，误差 ≈ 0 |
| 简易操作 | 正 + 侧两张 + 身高体重，端到端 ≤ 15 秒 |
| 用户校正率 | 建模后改围度的人 ≤ 30% |

只看「3D 好不好看」会做出虚模型；只看三围、不管肩宽立裆，会做出虚档案。两条一起过。胖体 / 特殊体型必须分层看，整体均值会掩盖高价值人群的误差。标定集仍按《04》《08》：≥200 人、专业量体师软尺、每人两遍取均值。

## 7. 落地顺序

避免一上来训大模型。

| 阶段 | 做完的定义 |
| --- | --- |
| 1. 正向模型 | 一具人台 + \(\beta\) + 22 个测量算子；手填围度能驱动 3D。`ManualProvider` 升级成这件事，不依赖相机 |
| 2. 经典反解 | 关键点 + 轮廓 + 身高，优化 \(\beta\)；腰腹靠侧照片 |
| 3. 合成图训 AI | 用自己的人台随机 \(\beta\)、衣服、光线渲染照片，训练回归器；200 人标定集纠偏，不是从零拟合人体统计 |
| 4. SDK 可选蒸馏 | 同一批照片让厂商出数当教师；教师不稳就丢，接口不变 |

与当前骨架批次对齐：业务链仍先跑通「手填档案 + 手填尺码表 → 推荐码」。正向人台属于算法域，挂在 `MeasureProvider` 上，不要在推荐引擎还没通时并行写相机。

## 8. 明确不做

- 把方便做成填 22 项或「身高体重即精准档案」；把精准做成扫描舱、裸体或必须两人拍摄
- 用胸腰臀三个数代表「已建档」
- 让用户一次手填 22 项当主路径；也不要把胸腰臀输入框当成「做不到拍照时的主替代」
- 假设旁边有人帮忙拍照；主流程必须一个人 + 倒计时靠墙拍
- 要求或引导裸体 / 仅内衣拍照；误传的裸体图必须端侧拦截并删除
- 把每张照片重建成独立高模当真相源
- 生产环境直接用未授权的 SMPL / SMPL-X 网格
- 业务代码绕过 `MeasureProvider` 调厂商 SDK
- 原图长留、把用户照片默认拿去训练、日志里打围度或照片地址
- C 端采集真实姓名、身份证、证件照、人脸核身；注册页出现「请输入真实姓名」
- 围度明文进日志；分享试穿图带围度数字
- 第一期用机器学习替换尺码推荐规则
