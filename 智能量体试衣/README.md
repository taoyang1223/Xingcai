# 智能量体试衣与按需制版平台（FitMe · 暂定名）

用户建立自己的 3D 人体模型，用它来**选对现成衣服的尺码**、**预览穿着效果**，未来还可以**自定义款式并生成可生产的服装版型**。

---

## 项目当前状态

**阶段**：需求与技术方案设计（P0 预研前）
**已产出**：产品需求文档 + 9 份技术文档
**待启动**：量体 SDK 供应商 POC、200 人标定集建设、淘宝取数合规路径确认

### 已确认的三项决策

| # | 决策 | 结论 |
| --- | --- | --- |
| 1 | 产品形态 | 移动 App（iOS + Android）+ Web 后台管理系统 + 统一服务端，三端同期 |
| 2 | 起步品类 | 不限品类，先做通用尺码推荐；定制与制版后移至第三期 |
| 3 | 建模能力 | 先采购第三方量体 SDK 验证需求，架构上保证可替换，再评估自研 |

## 三件最要紧的事

1. **淘宝取数路径未定** —— 这是核心链路的入口，方案不明确会让后面所有工作面临返工风险。淘宝对第三方抓取尺码表限制严格，需要在官方 API 资质、用户主动分享、浏览器插件三条路中确定可行方案，同时保证"手动录入尺码表"这条兜底路径永不下线。
2. **200 人标定集必须尽早开建** —— 它是验收量体 SDK 的唯一依据。没有它，供应商选型只能听厂商自说自话。需要预算、场地和专业量体师。
3. **合规不是上线前才处理的事** —— 人体照片与围度是敏感个人信息，原图删除、单独同意、字段加密、访问审计这四项是**架构级要求**，后补的成本是从头重做。

## 几个贯穿全项目的关键概念

| 概念 | 为什么重要 |
| --- | --- |
| **标准围度字段字典** | 全系统唯一的数据语言。厂商 SDK、尺码表、推荐引擎、客户端都必须归一到这套 key。见《02》附录 A |
| **平铺 vs 围量** | 淘宝尺码表最大的数据陷阱。"胸围 54cm"通常是平铺半宽，判错会让推荐结果差一倍 |
| **MeasureProvider 防腐层** | 决策 3 的架构保障。业务代码永不直接调用厂商 SDK，否则换供应商就要重写 |
| **置信度** | 宁可示弱不可误导。低置信度时给模糊表述，比给一个错误的确定结论好得多 |
| **松紧热力图** | 比渲染美图更有说服力的决策依据，且准确性只依赖尺寸计算，不依赖仿真质量 |
| **快照字段** | 推荐记录保存身体版本、尺码表版本、规则版本，保证任何一条历史推荐都能完整复现 |
