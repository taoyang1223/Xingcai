## 零、已确认的关键决策

以下决策已拍板，本文档后续内容均基于此展开：

| # | 决策项 | 结论 | 对方案的影响 |
| --- | --- | --- | --- |
| 1 | 产品形态 | **移动 App（iOS + Android）+ Web 后台管理系统 + 统一服务端**，三端同步建设 | 需新增「模块 J：后台管理系统」；服务端须从一开始就做成面向多端的统一 API 网关，不能写成 App 专用后端 |
| 2 | 起步品类 | **不限品类，先做通用尺码推荐，暂不碰定制生产** | 定制与制版（模块 F/G）整体后移至二期；但架构需预留，MVP 内埋点验证需求 |

> **"不限品类"的落地策略**：不限品类 ≠ 一次性支持所有品类。尺码表字段随品类差异极大（上衣看胸围肩宽、裤子看腰围裤长立裆、裙子看裙长腰围）。做法是：建立**按品类的尺码字段模板**，优先覆盖销量占比最高的 6 个类目（T恤/卫衣、衬衫、连衣裙、裤装、半裙、外套），预计可覆盖约 80% 的服装成交；模板之外的品类降级为"仅展示可比对的部位，并标注低置信度"，不直接拒绝服务。

## 一、项目背景与问题定义

### 1.1 用户痛点

线上买衣服最大的不确定性来自"尺码"。淘宝/天猫等平台上：

1. **尺码标准不统一**：同样标注 L 码，A 店的胸围 104cm，B 店的胸围 110cm；国标码、欧码、日码混用。
2. **尺码表信息残缺**：很多商品只给"衣长/胸围/肩宽"三个数，缺袖长、腰围、下摆围，更缺**版型松量**信息。
3. **用户不知道自己的净体尺寸**：绝大多数人只知道身高体重，不知道自己的胸围、腰围、臂长、肩宽。
4. **买家秀 ≠ 上身效果**：模特身材与自身差异大，无法预判"这件衣服穿我身上松紧如何、显不显胖、袖子会不会短"。
5. **退换货成本高**：服装类目退货率普遍 30%+，其中尺码问题占比过半，买家麻烦、卖家亏运费。

### 1.2 产品定位

用一句话概括：**让用户建立一个属于自己的、带真实尺寸的 3D 人体模型，用它来（1）选对现成衣服的尺码、（2）设计并预览自己想要的款式、（3）一键生成可生产的服装版型。**

产品覆盖三段价值链：

| 阶段 | 能力 | 解决的问题 |
| --- | --- | --- |
| 量体 | 拍照建模 + 自动测量 | 我到底是什么尺寸 |
| 选码 / 试穿 | 尺码推荐 + 虚拟试衣 | 这件衣服我穿哪个码、什么效果 |
| 定制 / 制版 | 参数化打版 + 工厂对接 | 没有合适的，就做一件合身的 |

### 1.3 商业价值假设（待验证）

- **C 端**：降低试错成本，会员制 / 定制成衣客单价。
- **B 端（商家）**：接入 SDK 后降低退货率，提高转化率，按调用量或按降低的退货金额分成。
- **工厂端**：聚合碎片化定制订单，形成"小单快反"的柔性供应链入口。

## 二、目标用户与典型场景

### 2.1 用户画像

| 画像 | 特征 | 核心诉求 |
| --- | --- | --- |
| 标准网购用户（主力） | 20–40 岁，每月线上买 1–3 件衣服 | 少退货、买对码 |
| 身材"非标"用户（高价值） | 高个/微胖/梨形/健身身材/孕产期 | 常规码永远不合身，愿意为定制付费 |
| 设计爱好者 / 小众穿搭 | 有明确审美，想改细节 | 改领型、改长度、换面料 |
| 中小服装商家 | 淘宝店主、独立设计师 | 想要低成本打版、降低退货 |
| 服装工厂 / 打版师 | 传统 CAD 作业 | 订单来源、自动化放码排料 |

### 2.2 核心用户故事

1. 作为一个网购用户，我拍两张照片、输入身高体重，就能得到自己的 3D 模型和 12 项身体围度数据。
2. 作为一个网购用户，我把一个淘宝商品链接粘贴进来，能看到"推荐 L 码，胸围处偏松 4cm，袖长可能短 1.5cm"这样的结论，并看到模型穿上后的效果图。
3. 作为一个身材非标用户，当所有尺码都不合适时，我能在推荐失败的地方直接进入"定制这件衣服"流程。
4. 作为一个设计爱好者，我能在一个基础款上调整领型、袖长、下摆、面料和颜色，实时看到穿在自己模型上的样子。
5. 作为一个用户，我确认款式后，系统生成版型文件与报价，下单后由合作工厂生产并配送。
6. 作为一个商家，我能把"试穿按钮"嵌入我的商品详情页，顾客点击后用自己的模型试穿我的货。

## 三、功能需求

> 优先级标记：**P0** = MVP 必须有；**P1** = 第二阶段；**P2** = 远期。

### 模块 A：用户与身体档案

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| A-1 | 账号体系 | P0 | 手机号 / 微信一键登录；身体数据与账号强绑定 |
| A-2 | 多人身体档案 | P1 | 一个账号下可建多个模型（本人、伴侣、父母、孩子），用于代买 |
| A-3 | 身体数据版本历史 | P1 | 记录体重/围度随时间变化，支持"三个月前的我" |
| A-4 | 隐私开关与数据删除 | P0 | 一键删除原始照片 / 删除全部身体数据；默认原始照片不长期留存 |
| A-5 | 穿衣偏好设置 | P0 | 偏紧身 / 常规 / 偏宽松；各品类可独立设置（上衣宽松、裤子修身） |

### 模块 B：人体建模与自动量体（核心技术模块）

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| B-0 | **量体能力适配层** | P0 | 依据决策 3，建模能力先采购第三方 SDK。必须定义统一内部接口 `MeasureProvider`（输入：照片/身高体重/性别；输出：标准化围度集 + 3D 网格 + 各部位置信度），供应商实现可插拔。**禁止任何业务代码直接调用厂商 SDK** |
| B-1 | 手动输入建模 | P0 | 输入身高、体重、性别、年龄，可选填胸/腰/臀，生成参数化人体。**这是兜底方案，必须先做** |
| B-2 | 双照片建模 | P0 | 正面 + 侧面全身照，自带拍摄引导（站姿、距离、着装、光线、背景） |
| B-3 | 自动围度测量 | P0 | 从 3D 模型上量取：颈围、肩宽、胸围、下胸围、腰围、臀围、大腿围、臂长、袖窿、背长、裤长（内缝/外缝）、身高 |
| B-4 | 测量结果人工校正 | P0 | 用户可手动修正任一围度，模型随之形变；并记录"用户修正量"作为算法反馈数据 |
| B-5 | 体型分类 | P1 | 自动判定沙漏型/梨型/苹果型/H 型/倒三角，作为版型匹配依据 |
| B-6 | 姿态与动作 | P1 | A-Pose / T-Pose / 站立自然姿态；P2 支持走动动画看垂坠感 |
| B-7 | 视频环绕扫描建模 | P2 | 手机绕身一周录像，精度更高 |
| B-8 | 深度/LiDAR 建模 | P2 | iPhone Pro 机型走 TrueDepth / LiDAR 通道 |
| B-9 | 形象个性化 | P2 | 发型、肤色、面部（可选择用抽象模特头，避免人脸数据风险） |

**精度目标（验收指标）**：关键围度（胸/腰/臀）平均绝对误差 ≤ 2.0cm、90 分位 ≤ 3.0cm；长度类（臂长/裤长）≤ 1.5cm。需用不少于 200 人的人工卷尺实测数据做标定集。

**第三方量体 SDK 选型要求（采购清单，供商务谈判用）**：

1. **精度可验证**：必须允许我方用自建 200 人标定集做验收测试（POC），不接受只看厂商宣传数据。
2. **输出必须含 3D 网格**：只给围度数字、不给可渲染模型的方案，无法支撑后续虚拟试衣，直接排除。
3. **端侧/私有化部署选项**：优先支持端侧推理或可私有化部署，照片不出我方环境——这是合规底线（见 5.2）。若只能走厂商云端，必须签数据处理协议（DPA）并明确不得留存、不得用于其训练。
4. **计费模式**：按调用量计费需测算规模化后的成本（目标建模单次成本 ≤ 0.5 元），并争取买断/包年选项。
5. **数据主权**：我方用户的照片、围度、修正反馈数据所有权归我方，厂商不得二次使用。
6. **退出成本**：明确网格格式（glTF/OBJ/自有格式）与围度字段口径，确保更换供应商时历史模型可迁移。
7. 建议同时接入 **2 家**供应商做 A/B，既压价也降低单点依赖。

### 模块 C：商品与尺码数据

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| C-1 | 商品链接解析 | P0 | 粘贴淘宝/天猫商品链接或分享口令，抓取标题、主图、尺码表、材质成分 |
| C-2 | 尺码表结构化 | P0 | 尺码表常以**图片**形式存在，需 OCR + 表格还原 + 字段归一化（"胸围/净胸围/衣宽"等叫法统一） |
| C-2b | 品类尺码字段模板 | P0 | 按决策 2 的"不限品类"策略：为每个品类定义必测字段与可选字段（上衣=胸围/肩宽/衣长/袖长；裤装=腰围/臀围/裤长/立裆/脚口；裙装=腰围/臀围/裙长）。模板在后台可配置，运营可新增品类而无需发版 |
| C-3 | 手动录入尺码表 | P0 | 解析失败时允许用户拍照/手填，作为兜底与训练数据 |
| C-4 | 品牌尺码档案库 | P1 | 沉淀各品牌各品类的尺码偏差（"该店普遍偏小半码"） |
| C-5 | 面料弹性与版型标签 | P1 | 从成分（氨纶含量）、描述关键词推断弹性与版型（修身/直筒/宽松/Oversize） |
| C-6 | 商品 3D 化 | P1 | 由尺码表 + 款式模板反推近似 3D 服装；P2 支持商家上传真实版片/3D 模型 |
| C-7 | 其他平台支持 | P2 | 京东、抖音电商、拼多多、SHEIN |

> ⚠️ **技术与合规风险（必须在方案阶段确认）**：淘宝开放平台对第三方抓取商品数据有严格限制。需要评估三条路径：(a) 申请淘宝开放平台 / 淘宝联盟正式 API 资质；(b) 由用户主动"分享到本 App"并在客户端本地解析；(c) 浏览器插件形态，仅在用户自己浏览时读取页面。**不得采用大规模爬虫方案。**

### 模块 G：制版与生产（本项目的差异化壁垒）

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| G-1 | 参数化自动打版 | P0 | 由「净体尺寸 + 款式参数 + 松量规则 + 面料缩率」生成 2D 版片；基于成熟制版体系（如日本文化式原型 / 国标比例法） |
| G-2 | 版片校验 | P0 | 缝合边长匹配校验、袖窿与袖山吃势校验、对位点、缝份自动加放、丝缕线、纱向标注 |
| G-3 | 工业文件导出 | P0 | **DXF-AAMA / ASTM** 格式（可导入 ET 服装 CAD、富怡、格柏 Gerber、Lectra、CLO3D）；PDF 分页打印版（家庭打印机 A4 拼接）；SVG |
| G-4 | 工艺单生成 | P1 | 款式图、物料清单 BOM、尺寸表、缝制工艺说明、洗标信息 |
| G-5 | 用料与排料 | P1 | 自动排料（marker making）估算面料用量与成本 |
| G-6 | 放码 | P1 | 面向商家：由样版自动推档出 S–XXL 全套号型 |
| G-7 | 试版闭环 | P1 | 首件白坯样/成衣寄样 → 用户反馈 → 版型微调 → 存为"我的专属基础版" |
| G-8 | 工厂对接 | P1 | 订单派单、产能与工期、进度追踪（裁剪/缝制/整烫/质检/发货） |
| G-9 | 报价引擎 | P0 | 面料成本 + 工艺复杂度 + 工时 + 物流 + 毛利 → 实时报价 |

> **重要说明**：模块 G 的"版型质量"无法完全靠算法保证，必须引入**专业打版师复核**环节（至少在早期 100% 人工复核，逐步转为抽检）。这是产品口碑的生死线。

### 模块 H：订单与售后

| 编号 | 功能 | 优先级 | 说明 |
| --- | --- | --- | --- |
| H-1 | 定制订单流程 | P0 | 下单 → 支付 → 确认版型 → 生产 → 发货 → 签收 |
| H-2 | 定制商品售后规则 | P0 | 定制品不适用七天无理由，需在下单前**显著告知并单独确认**；同时提供"合身保障"（尺寸偏差超过承诺值免费返修/重做） |
| H-3 | 收货反馈 | P0 | 合身度评分 + 部位问题标注，回流给建模与制版算法 |
| H-4 | 返修 / 改衣 | P1 | 局部改尺寸并更新用户专属版型 |

### 模块 J：Web 后台管理系统（依据决策 1，与 App 同期建设）

后台不是"上线后再补"的附属品。本产品的核心资产——尺码表、品类模板、松量规则、款式库、面料库——都靠运营与打版师在后台维护，**后台的完备度直接决定业务能不能跑起来**。因此后台随 MVP 同期交付。

## 四、核心业务流程

### 4.1 选码流程（高频主链路）

```
打开 App
  └─ 是否已有身体模型？
       ├─ 否 → 建模引导（拍照 / 手输）→ 测量结果确认与微调 → 模型生成
       └─ 是 ↓
  粘贴商品链接 / 从淘宝分享进入 / 扫描商品
  └─ 解析商品与尺码表
       ├─ 成功 → 尺码推荐引擎
       └─ 失败 → 引导用户拍摄尺码表（OCR）或手填
  └─ 输出：推荐码 + 部位级诊断 + 3D 试穿效果 + 松紧热力图
       ├─ 满意 → 跳转淘宝下单（并记录以便收货后回访）
       └─ 都不合适 → 「没有合适的？定制一件」→ 进入 4.2
```

### 4.2 定制制版流程

```
选择基础款式 → 参数化调整（领/袖/长度/收腰）→ 选面料与颜色
  → 在自己的模型上实时预览 → 确认设计
  → 系统按净体尺寸 + 款式松量自动生成版片
  → 打版师复核（早期必经）→ 报价确认 → 支付
  → 工厂生产（进度可查）→ 发货 → 收货反馈
  → 合身则存为「我的专属版型」，下次下单直接复用
```

### 4.3 数据反馈闭环（产品长期壁垒）

```
用户实际穿着反馈 ──┬─→ 修正建模误差（该体型该部位系统性偏差）
                   ├─→ 修正品牌尺码偏差档案
                   ├─→ 修正松量规则库
                   └─→ 修正推荐模型权重
```

## 五、非功能性需求

### 5.1 性能

| 指标 | 目标 |
| --- | --- |
| 照片建模端到端耗时 | ≤ 30s（P95），超过 10s 需有进度提示 |
| 尺码推荐接口响应 | ≤ 500ms（P95） |
| 商品链接解析 | ≤ 3s |
| 3D 渲染帧率 | 移动端 ≥ 30 FPS（中端机型，如骁龙 7 系） |
| 自动打版生成 | ≤ 60s |
| 系统可用性 | ≥ 99.5% |

### 5.2 数据安全与合规（**高风险项，必须前置设计**）

1. **人体照片与体型数据属于敏感个人信息**，适用《个人信息保护法》《数据安全法》；若采集人脸，还需遵守《人脸识别技术应用安全管理规定》。
2. 采集须取得**单独同意**（不能混在统一用户协议里勾选），并明示用途、存储期限、第三方共享情况。
3. **默认不存储原始照片**：建模完成后立即删除原图，仅保留不可逆的模型参数；如需留存训练数据，必须二次单独授权并脱敏。
4. 优先考虑**端侧建模**（模型跑在手机本地），照片不出设备，这既是合规优势也是营销卖点。
5. 传输 TLS 1.3，存储加密（体型数据字段级加密），访问审计留痕。
6. 提供账号注销与数据彻底删除，承诺 T+N 日内清除备份。
7. 未成年人模式：不满 14 周岁需监护人同意；建议 MVP 直接不支持未成年人建模。
8. 模型形象默认使用**无面部特征的抽象人台**，规避人脸风险。
9. **第三方量体 SDK 的合规连带责任**：依据决策 3 采购外部 SDK，须在隐私政策中列明该第三方身份与处理目的，签署数据处理协议，约定不得留存、不得用于其模型训练、不得境外传输；优先选择端侧或私有化部署方案。**厂商违规，责任在我方**，这一点须在合同中明确赔偿条款。
10. 后台人员访问用户身体数据须走审批 + 留痕（见 J-2、J-6），并做最小化与脱敏展示。

### 5.3 兼容性

- 移动 App：iOS 14+、Android 10+（覆盖约 95% 在网机型）。
- Web 后台：Chrome / Edge 近两年版本为主（内部系统，不承诺 Safari 与移动端适配），需支持 1440px 及以上分辨率，1280px 可用。
- 3D 预览：WebGL 2.0 / 原生 Metal-Vulkan；低端机降级为服务端渲染出图。
- 微信小程序：本期不做，但服务端 API 设计需预留（决策 1 未包含小程序，后续若做不应重构后端）。

### 5.4 可扩展性

- 尺码推荐、建模、打版三大引擎解耦为独立服务，可单独迭代与灰度。
- 款式与规则**配置化**（款式模板、松量规则、面料参数以配置数据存储，而非硬编码），支持打版师不改代码地新增款式。
- 预留多品类扩展：内衣、童装、鞋（脚型扫描）、眼镜。

## 六、技术方案建议（供评估，非最终定稿）

> 依据决策 1（App + Web 后台 + 服务端）与决策 3（先采购后自研），架构的第一原则是：**业务逻辑与建模能力解耦、服务端与端形态解耦**。

### 6.1 整体架构分层

```
  iOS App        Android App        Web 后台管理       (预留：小程序 / 商家 SDK)
      └───────────────┴──────────────────┴─────────────────────┘
                              │
                    API 网关（鉴权 / 限流 / 审计）
                              │
      ┌───────────┬───────────┼───────────┬────────────┬───────────┐
   用户服务    商品服务    推荐引擎    量体服务      内容服务    管理后台服务
                              │            │
                              │     MeasureProvider 适配层（B-0）
                              │      ├─ 供应商A SDK
                              │      ├─ 供应商B SDK
                              │      └─ 自研引擎（远期替换，接口不变）
                    规则/配置中心（松量规则、品类模板、Feature Flag）
```

C 端 App 与 Web 后台**共用同一套服务端与鉴权体系**，仅权限域不同；后台服务可独立部署并限制网络入口。

### 6.2 技术选型建议

| 层 | 建议方案 | 备注 |
| --- | --- | --- |
| 移动 App | Flutter 或 React Native 主体 + 原生插件（相机、3D 渲染、量体 SDK） | 三端并行且团队有限时，跨端可省约 40% 客户端工作量；但相机与 3D 部分必然要写原生，选型时要确认量体 SDK 是否提供跨端封装 |
| Web 后台 | React + TypeScript + Ant Design Pro | 后台是表格/表单/审核队列密集型，成熟中后台框架能显著提速；不要自己造轮子 |
| API 网关 | 统一鉴权、限流、请求审计，区分 C 端 token 与后台 token | 后台接口与 C 端接口物理隔离，后台仅内网/VPN 可达 |
| 参数化人体 | 先用采购 SDK 的输出；远期自研时再评估 SMPL / SMPL-X | SMPL 系列有**商用授权**限制，自研阶段需评估授权费或改用可商用的 PCA 体型基 |
| 单目人体重建 | 采购为主。自研预研方向：关键点检测（MediaPipe/HRNet）+ 轮廓分割 + 身高先验 → 拟合形体参数 | 双视角（正+侧）显著提升腰腹精度 |
| 围度测量 | 在拟合网格上按解剖标志点做测地线截面周长 | 需区分"净体围"与"卷尺松量"；即便用采购 SDK，也要自己复算一遍以统一口径 |
| 布料仿真 | XPBD / Position-Based Dynamics；离线可用 NVIDIA Warp、Blender Cloth；商业可评估 CLO / Style3D SDK | 实时端建议先做静态"变形贴合"近似，不做全物理 |
| 3D 渲染 | three.js / Babylon.js（Web），Filament / SceneKit（原生），glTF + Draco 压缩 | |
| 自动打版 | 规则引擎 + 几何库（Python + shapely / 自研曲线库），基于文化式原型或国标比例公式 | 输出 DXF-AAMA，用 ezdxf 等库 |
| 尺码表 OCR | 表格识别（PaddleOCR PP-Structure 等）+ 字段归一化词典 + 人工兜底标注 | |
| 后端 | 微服务（Python 负责算法，Go/Java 负责交易），消息队列处理建模等耗时任务 | 建模是长耗时任务，必须异步化 + 进度推送，不能让 App 同步等待 |
| 存储 | 业务库 PostgreSQL/MySQL；模型资产对象存储；向量库用于体型相似检索 | 身体数据字段级加密；原始照片走独立短生命周期桶，自动过期删除 |
| 算法平台 | GPU 推理服务（建模、仿真），支持任务队列与弹性扩缩 | 采购期可能由厂商承担，自研期需自建 |
| 配置中心 | 松量规则、品类字段模板、Feature Flag 统一配置化，支持版本与灰度 | 对应 J-4/J-5/J-15，让运营与打版师改规则不需要发版 |

## 七、MVP 范围建议（第一版做什么、不做什么）

**MVP 目标：验证"用户愿意为更准的尺码建议花时间建模"这一核心假设。**（依据决策 2，MVP 只做通用尺码推荐，不含定制生产）

✅ MVP 包含：

**App 端**

1. 账号 + 隐私单独授权（A-1/A-4/A-5）
2. 手动输入建模（B-1）+ 基于采购 SDK 的双照片建模（B-0/B-2/B-3/B-4）
3. 商品链接解析 + 尺码表 OCR + 手动兜底（C-1/C-2/C-2b/C-3）
4. 基础尺码推荐与部位级诊断（D-1/D-2/D-3）
5. 简化 3D 预览 + 松紧热力图 + 同款不同码对比（E-1/E-2/E-5，先不做物理仿真）
6. 收货合身度反馈（H-3、D-7）

**Web 后台（同期交付，缺了业务跑不动）**

7. 权限与审计（J-1/J-2）
8. 商品与尺码表人工审核纠错队列（J-3）
9. 品类字段模板与松量规则配置（J-4/J-5）
10. 用户档案脱敏查询（J-6）、效果监控看板（J-7）、反馈工单（J-8）
11. 量体 SDK 供应商切换与 A/B（J-9）

❌ MVP 不做：定制设计与制版、AR 试穿、走动动画、布料物理仿真、叠穿、设计师市场、商家 SDK、放码排料、淘宝以外平台、小程序。

⚠️ 定制制版（模块 F/G）作为**第二阶段**，但 MVP 里要埋入口做需求验证：当推荐结果是"没有合适尺码"时，展示"想要一件完全合身的？"按钮，统计点击率与留资量——这个数字决定第二阶段是否值得投入，也决定届时是自建打版团队还是找 C2M 供应链合作。

### 阶段规划

| 阶段 | 周期（估） | 交付 | 验证目标 |
| --- | --- | --- | --- |
| P0 选型与预研 | 4–6 周 | 量体 SDK 供应商 POC 对比（≥2 家，用 200 人标定集实测）、淘宝取数合规路径确认、后台数据模型设计 | 采购 SDK 精度能否 ≤2cm；商品数据能否合规拿到 |
| P1 MVP | 4–5 个月 | App（iOS+Android）+ Web 后台 + 服务端，小范围内测 500–2000 人 | 建模完成率、推荐采纳率、退货率下降幅度 |
| P2 规模化与品类扩展 | 3 个月 | 覆盖 6 大品类模板、品牌尺码档案库、协同过滤、分享裂变 | 解析成功率 ≥80%、留存 |
| P3 定制闭环 | 3–4 个月 | 款式设计 + 自动打版 + 1–2 家工厂合作，限品类起步 | 定制转化率、首件合身率、复购 |
| P4 平台化 | 6 个月+ | 商家 SDK、开放 API、设计师市场、自研量体引擎替换 SDK | B 端付费意愿、单次建模成本下降 |

> **三端并行的排期提醒**：App 双端 + Web 后台 + 服务端同期开发，人力是最大约束。建议排期上让**服务端与后台先行 2–3 周**（后台 J-3/J-4/J-5 先跑起来，运营才能提前积累尺码表与规则数据，避免 App 上线时"有壳无货"）。

## 九、主要风险与应对

| 风险 | 等级 | 影响 | 应对 |
| --- | --- | --- | --- |
| 淘宝数据获取受限/被封 | **高** | 核心链路断裂 | 优先走官方合作/联盟 API；同时保证"手动录入尺码表"路径永远可用；探索插件与用户主动分享形态 |
| 建模精度不达标 | **高** | 推荐不可信，口碑崩塌 | 预研阶段先做精度验证；提供人工校正；对低置信度部位坦诚标注"不确定" |
| 用户不愿拍全身照 | **高** | 转化漏斗前置流失 | 端侧处理+不留原图+抽象人台形象；提供纯数值输入兜底；用"拍照只需 10 秒"降低心理门槛 |
| 自动版型不可生产 | **高** | 定制退货、成本失控 | 早期 100% 打版师复核；限定品类起步；建立白坯样试版流程 |
| 商品尺码表本身不准 | 中 | 推荐错误但责任在商家 | 众包实测数据校正；标注品牌可信度；推荐时给出置信度 |
| 定制生产周期长（2–4 周） | 中 | 用户流失 | 明确预期管理；从工期短的品类切入；探索区域快反工厂 |
| 个人信息合规处罚 | **高** | 法律风险 | 单独同意、端侧优先、不存原图、通过安全评估；上线前做合规审查与个人信息保护影响评估（PIA） |
| **第三方量体 SDK 单点依赖** | **高** | 涨价、停服、精度不达标即全线瘫痪 | B-0 适配层强制解耦；同时接入 2 家做 A/B；合同锁定价格与数据主权；自研作为长期解绑路径 |
| **三端并行导致人力摊薄** | 中高 | 三个端都做不完整 | 后台先行、App 跨端框架、明确 MVP 砍掉的清单不再讨论；后台只做 P0 的 9 项 |
| 不限品类导致尺码表字段发散 | 中 | 解析成功率上不去 | 品类字段模板 + 优先覆盖 6 大类目；模板外品类降级为低置信度提示而非报错 |
| SMPL 等模型商用授权 | 中 | 法务/成本 | 自研阶段前确认授权方案或采用可商用替代 |
| 3D 渲染在低端机卡顿 | 中 | 体验差 | 服务端渲染降级方案 |

## 十、待确认的开放问题

已确认：产品形态（App + Web 后台 + 服务端）、起步品类（不限品类、先做通用选码）、建模能力来源（先采购 SDK）。剩余待决：

1. **淘宝取数路径**（**最紧急，卡住核心链路**）：是否具备申请淘宝开放平台/淘宝联盟资质的主体条件？若不具备，MVP 是否接受"用户从淘宝分享到 App + 尺码表截图 OCR"这一体验略重的方案？
2. **变现**：C 端订阅制 / 导购佣金（淘宝联盟返佣）/ 定制成衣差价 / B 端 SaaS，主次如何排？这决定 MVP 要不要做支付与分佣模块。
3. **是否采集人脸**：默认不采集、用抽象人台（建议），还是为了"真实感"采集？直接决定合规复杂度等级。
4. **冷启动**：内测 500–2000 人从哪来？是否先与 1–2 个淘宝店铺合作做"推荐—下单—退货率"的闭环试点？
5. **200 人标定集**：谁来组织人工卷尺实测？这是验收量体 SDK 的前提，需要预算与场地，建议 P0 阶段就启动。
6. **二期制版路径**（可延后，但影响架构预留）：自建打版团队 + 合作工厂，还是与现有 C2M 定制供应链合作？
7. **团队配置**：三端并行需要的最小团队（客户端 2–3、后端 2–3、前端 1–2、算法 1–2、产品 1、设计 1、运营/审核 1–2）是否到位？
