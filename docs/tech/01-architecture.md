# 01 · 技术架构设计文档

> 项目：智能量体试衣与按需制版平台（FitMe）
> 版本：v0.1 草案
> 上游依据：《产品需求文档》第零章三项决策、第六章技术建议
> 适用阶段：P0 预研 ~ P1 MVP

---

## 1. 架构约束（先说清楚边界）

本架构的所有设计都服从以下四条硬约束，它们来自产品决策而非技术偏好：

| 约束 | 来源 | 架构含义 |
| --- | --- | --- |
| C1 三端同期：iOS App + Android App + Web 后台 | 决策 1 | 服务端必须是面向多端的统一 API 层，不能是"App 后端 + 后台后端"两套 |
| C2 量体能力来自采购的第三方 SDK，将来可能自研替换 | 决策 3 | 量体必须是可插拔的**防腐层**，业务域绝不感知厂商 |
| C3 MVP 不做定制生产，但二期要做 | 决策 2 | 订单、支付、工厂域现在不建，但领域边界要预留，不能把"推荐"和"交易"揉在一起 |
| C4 人体照片与围度属于敏感个人信息 | PRD 5.2 | 数据分域存储、字段级加密、访问审计是架构级要求，不是后补功能 |

**一条反约束**：团队规模有限而端很多，因此 **MVP 阶段不做微服务**。过早拆分会把有限人力消耗在分布式事务、服务治理和联调上。做法是「**模块化单体 + 独立算法服务**」，用清晰的模块边界换取将来低成本拆分。

---

## 2. 架构目标与原则

**目标**（可验证的，非口号）：

1. 新增一个电商平台的商品解析，不改推荐引擎代码。
2. 更换量体供应商，改动范围不超过 1 个适配器模块。
3. 运营新增一个品类、调整一条松量规则，不需要发版。
4. 后台系统被攻破，也拿不到明文身体数据和原始照片。
5. 二期把定制交易拆成独立服务时，不需要重写用户与推荐模块。

**原则**：

- **依赖倒置**：业务域定义接口，外部实现适配（量体 SDK、电商平台、OCR、支付都是"可替换的外设"）。
- **配置优于代码**：品类模板、松量规则、开关、文案走配置中心。
- **异步优于同步**：建模、OCR、渲染都是长耗时任务，一律任务化。
- **数据最小化**：能不存的不存，能脱敏的脱敏，能端侧算的不上云。

### 3.2 为什么是"模块化单体 + 独立算法服务"

算法服务独立出来，是因为它和业务服务的**技术栈、伸缩特性、部署节奏都不同**：Python 生态、需要 GPU、调用量波动大、迭代频繁。而业务模块之间调用频繁、事务一致性要求高，放在一个进程里最省事。

模块化单体的纪律要求（**必须在 Code Review 中强制执行，否则单体必然腐化**）：

1. 每个模块只暴露 `service` 包作为对外入口，其他模块不得直接访问其 `repository` 或数据表。
2. 模块间调用走接口，不走具体实现。
3. 每个模块拥有自己的表，**跨模块不做 JOIN**，需要关联数据时调对方接口。
4. 目录结构即边界，CI 中加静态检查（如 `go-arch-lint`）拦截越界 import。

做到这四条，二期拆服务时把模块目录整体搬走即可。

## 4. 模块划分与职责

| 模块 | 职责 | 拥有的核心数据 | 不负责什么 |
| --- | --- | --- | --- |
| `identity` | 注册登录、Token、账号注销、同意书（Consent）记录 | 用户、授权凭证、同意记录 | 不存身体数据 |
| `body` | 身体档案、建模任务编排、围度存取与校正、体型分类 | 身体档案、围度、模型资产引用、建模任务 | 不实现建模算法 |
| `catalog` | 商品解析、尺码表结构化、品类模板、品牌档案 | 商品、尺码表、品类、品牌偏差 | 不做推荐计算 |
| `recommend` | 尺码推荐、部位诊断、置信度、试穿数据准备 | 推荐记录、松量规则引用 | 不抓商品、不建模 |
| `feedback` | 合身反馈、工单、数据回流 | 反馈、工单 | 不改算法参数 |
| `content` | Banner、公告、穿搭内容 | 内容 | — |
| `config` | 品类模板、松量规则、Feature Flag、版本与灰度 | 配置及其版本 | — |
| `admin` | 后台聚合接口、审核队列、看板取数 | 管理员、角色权限 | 不重复实现业务逻辑，只编排 |
| `audit` | 全局审计日志采集与查询 | 审计日志（只追加） | — |
| `measure-svc`(独立) | 量体适配层，统一围度输出 | 无持久化（结果回写 body） | 不做业务判断 |
| `ocr-svc`(独立) | 尺码表图片识别与表格还原 | 无持久化 | 不做字段语义归一（归一在 catalog） |
| `render-svc`(独立) | 3D 穿着效果与热力图出图（低端机降级用） | 无持久化 | — |

> 二期新增：`design`（款式）、`pattern`（制版）、`order`（交易）、`factory`（生产）、`payment`。其中 `order`/`payment` **必须**独立成服务，不进单体。

## 5. 技术选型

| 层次 | 选型 | 理由 | 备选/风险 |
| --- | --- | --- | --- |
| 移动 App | **Flutter 3.x** 主体 + 原生插件 | 三端并行人力紧张，跨端省约 40% 客户端工作量；UI 一致性好 | 3D 与相机必须写原生；若采购的量体 SDK 无 Flutter 封装，需自己写 Platform Channel（**选型 POC 时务必确认**） |
| App 内 3D | 原生 PlatformView：iOS SceneKit/Metal、Android Filament；glTF + Draco | Flutter 自身 3D 生态不成熟，硬上会踩坑 | 低端机降级为 `render-svc` 服务端出图 |
| Web 后台 | **React 18 + TypeScript + Ant Design Pro + Vite** | 后台是表格/表单/审核队列密集型，成熟中后台框架提速最明显 | 不要自研组件库 |
| 网关 | APISIX 或云厂商 API 网关 | 鉴权、限流、审计开箱即用 | 后台入口与 C 端入口物理分离 |
| 业务服务 | **Go 1.22 + Gin**（模块化单体） | 已由《00 技术路线》锁定；骨架期不用 Kratos/网关 | 流量上来后再前置 APISIX |
| 算法服务 | **Python 3.11 + FastAPI + gRPC** | 视觉/OCR 生态在 Python | GPU 资源成本 |
| 数据库 | **PostgreSQL 15** | JSONB 存尺码表这类半结构化数据极合适；扩展生态好（pgcrypto、pgvector） | MySQL 亦可，但 JSONB 与 vector 能力弱 |
| 缓存 | Redis 7 | 会话、限流、推荐结果缓存、热点商品 | |
| 消息队列 | **Redis Stream**（接口抽象） | 《00》锁定：骨架期不上 Kafka/RocketMQ | 换实现时只改适配器 |
| 对象存储 | OSS/S3，**分两个桶** | `assets-bucket`（模型网格，长期）与 `raw-photo-bucket`（原图，生命周期 1 小时自动删） | 合规硬要求，见文档 06 |
| 搜索/分析 | P1 暂不引入；P2 ClickHouse | 避免过早复杂化 | |
| 部署 | **Docker Compose**（镜像化） | 《00》锁定：骨架期不上 K8s | 内测后再上托管 K8s |
| 可观测 | OpenTelemetry + Prometheus + Grafana + Loki + Sentry | 统一埋点标准 | 见文档 07 |

## 6. 核心链路设计

### 6.1 建模链路（异步 + 强合规）

```
App                  Gateway/body          MQ        measure-worker      measure-svc/厂商
 │ 1.申请上传凭证 ────────►│
 │ ◄── 直传 STS 凭证(限 raw-photo 桶, 有效期 5min)
 │ 2.照片直传 OSS ─────────────────────────────────────►(raw-photo-bucket)
 │ 3.提交建模任务(photo_key,身高体重,consent_id) ─►│
 │ ◄── job_id (202 Accepted)        创建 job ──► 投递消息 ─►│
 │ 4.轮询/长连接查 job 状态 ──►│                            │ 拉取照片
 │                                                          │ 调 MeasureProvider ──►│
 │                                                          │ ◄── 围度+网格+置信度  │
 │                                                    写 body_measurements(加密)
 │                                                    上传网格至 assets-bucket
 │                                                    **删除原图**、写审计
 │ ◄── 状态 SUCCEEDED + 围度 + 模型 URL(签名, 短有效期)
 │ 5.用户校正围度 ───────►│ 记录 user_corrected 与修正量(回流算法)
```

关键设计点：

- **照片直传不过业务服务器**，减少一处留存风险与带宽成本。
- **原图删除是任务的一个必需步骤**，失败要重试并告警；同时桶本身配生命周期兜底。
- 任务有明确状态机：`PENDING → RUNNING → SUCCEEDED / FAILED / TIMEOUT`，超过 90s 判超时并给用户兜底方案（转手动输入）。
- 建模结果带**逐部位置信度**，低置信部位在 UI 上要提示用户复核（PRD B-4）。

### 6.2 选码链路（同步 + 缓存）

```
App ──粘贴链接──► catalog.ParseProduct
                    ├─ 命中商品缓存(product_hash)？ → 直接返回
                    ├─ 走合规取数通道 → 得到标题/主图/尺码表(可能是图片)
                    ├─ 图片尺码表 → ocr-svc → 表格还原
                    ├─ 字段归一化(按品类模板 + 别名词典)
                    └─ 置信度低 → 入后台人工审核队列(J-3)，同时向用户降级提示
                         │
                    recommend.Suggest(body_profile_id, product_id, preference)
                         ├─ 取松量规则(config, 按 品类×版型×弹性)
                         ├─ 取品牌偏差(catalog)
                         ├─ 逐部位差值计算 + 评分 + 置信度
                         └─ 输出推荐码/备选/部位诊断/风险
                         │
                    渲染：客户端本地形变 + 热力图（低端机走 render-svc）
```

**缓存策略**：同一商品的解析结果全局共享（按 `平台+商品ID+尺码表版本哈希` 缓存 7 天）；推荐结果按 `身体档案版本 × 商品版本 × 偏好` 缓存 1 天，身体数据一变即失效。这两层缓存能挡掉绝大部分重复计算——爆款商品会被成千上万人查询。

### 6.3 反馈回流链路

收货后回访 → `feedback` 落库 → 事件 `fit_feedback.created` → 异步聚合任务：

- 更新品牌/店铺尺码偏差档案（`catalog.brand_size_bias`）
- 累积松量规则的调整证据（人工在后台 J-5 确认后生效，**不做自动改规则**）
- 沉淀建模误差样本（某体型某部位系统性偏差）

> 规则调整坚持"算法给建议、人工做决定"，避免脏数据自动污染核心规则。

## 7. 外部依赖与隔离

| 依赖 | 风险 | 隔离手段 |
| --- | --- | --- |
| 量体 SDK（2 家） | 涨价、停服、精度差异 | `MeasureProvider` 接口 + 配置化分流（J-9）；结果格式统一为内部标准；每家的调用成功率/耗时/精度单独监控 |
| 电商取数（淘宝） | 合规与可用性，随时可能断 | 封装 `ProductSource` 接口，至少三种实现：官方 API、用户分享解析、用户手动录入。**手动录入永不下线**，作为终极兜底 |
| OCR | 识别率波动 | 自建服务 + 云厂商 OCR 双通道；低置信度进人工队列 |
| 短信/推送/支付 | 一般 | 标准封装，不赘述 |

所有外部依赖统一要求：**超时控制、重试上限、熔断降级、独立监控面板、成本计量**。第三方调用成本要能按天出账，否则 SDK 调用费会失控。

## 8. 容量与成本估算（用于选型与预算）

假设 MVP 内测 2000 人、公测 10 万注册用户：

| 项 | 估算 | 说明 |
| --- | --- | --- |
| 建模调用 | 10 万人 × 1.3 次 = 13 万次 | 人均建模 1.3 次（含重建） |
| SDK 成本 | 13 万 × 0.5 元 = 6.5 万元 | 单次成本必须压到 0.5 元内，否则模式不成立 |
| 商品解析 | 10 万人 × 8 次/月 = 80 万次/月 | 缓存命中率预计 60%+，实际回源 ~30 万次 |
| 推荐计算 | 峰值 200 QPS | 纯计算 + 缓存，单机可扛，无需过度设计 |
| 模型资产存储 | 10 万 × 2MB = 200GB | glTF+Draco 压缩后单模型约 1–3MB |
| 数据库 | 单实例主从即可 | 百万级行数，远未到分库分表 |

**结论：MVP 阶段的瓶颈不在并发，在 SDK 单次成本与 OCR 准确率。** 架构上不要为并发过度设计。

## 9. 演进路线

| 阶段 | 架构动作 | 触发条件 |
| --- | --- | --- |
| P1 MVP | 模块化单体 + 3 个算法服务 | — |
| P2 | 拆出 `catalog` 为独立服务（解析任务重、迭代快）；引入 ClickHouse 做分析 | 解析任务占用业务实例资源、看板查询拖慢主库 |
| P3 定制 | 新建 `order`/`payment`/`pattern`/`factory` 独立服务；引入分布式事务（Saga） | 定制业务上线 |
| P4 | `body` 与自研量体引擎替换 SDK；开放平台网关独立 | SDK 成本超过自研成本，或 B 端接入量上来 |

**明确记录的技术债**：MVP 的推荐引擎是规则驱动的，缺乏机器学习；这是刻意的——没有数据之前上模型是自欺欺人。数据积累到 5 万条以上合身反馈后再评估模型化。

## 10. 架构决策记录（ADR 摘要）

| ID | 决策 | 理由 | 状态 |
| --- | --- | --- | --- |
| ADR-01 | MVP 采用模块化单体而非微服务 | 团队规模与迭代速度优先 | 已定 |
| ADR-02 | 量体能力经 `MeasureProvider` 防腐层接入 | 决策 3 要求可替换 | 已定 |
| ADR-03 | 原始照片直传 OSS 且 1 小时内删除 | 合规底线 | 已定 |
