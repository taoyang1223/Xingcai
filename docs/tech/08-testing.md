# 08 · 测试策略与质量保障

> 本项目的特殊性：**核心功能的正确性无法用传统断言验证**。"推荐 L 码"对不对，不是单元测试能回答的问题，需要一套精度评测体系。本文档因此分两条线：常规软件测试 + 算法质量评测。

## 2. 单元测试重点

业务代码的单测按常规做，这里只列**必须高覆盖**的部分：

| 模块 | 必测内容 | 覆盖率 |
| --- | --- | --- |
| 推荐引擎 | PartScore 分段函数边界、硬约束一票否决、置信度计算、降级矩阵每一行 | ≥90% |
| 尺码归一化 | 别名映射、平铺/围量判定、单位换算、单调性校验、异常值拦截 | ≥90% |
| 量体适配器 | 字段映射、缺失补全、异常输出拦截（每家供应商一套） | ≥85% |
| 松量规则匹配 | 四维查找与 fallback 逻辑 | ≥85% |
| 合规相关 | 同意校验、脱敏函数、加解密、原图删除 | **100%** |

> 合规相关代码要求 100% 覆盖，并且要有**反向用例**：没有同意时必须抛错、脱敏函数遇到未知字段时必须默认脱敏而不是默认放行。安全逻辑的默认值应当是"拒绝"。

### 典型边界用例（尺码归一化）

| 输入 | 期望 |
| --- | --- |
| 表头"胸围 54cm"，品类=T恤 | 判定为平铺，归一化为 108cm |
| 表头"胸围 108cm"，品类=T恤 | 判定为围量，保持 108cm |
| 尺码 S=100, M=98, L=104 | 单调性失败 → 进人工审核 |
| 尺码 S=96, M=100, L=130 | 档差异常 → 进人工审核 |
| 单位 inch | 换算为 cm 并保留一位小数 |
| 表头"均码" | size_order=0，正常处理 |
| 空表 / 全 OCR 失败 | parse_status=failed，不写脏数据 |

## 3. 接口与集成测试

- 基于 OpenAPI 自动生成用例骨架，覆盖每个接口的：正常、参数缺失、类型错误、越权、未登录、限流、幂等重放。
- **越权测试必须自动化且每次回归**：用 A 用户的 Token 访问 B 用户的 `profile_uid`，必须 404/403。这类 IDOR 漏洞是本产品最高危的漏洞类型（文档 06 第 8 节）。
- 第三方依赖用 Mock/Stub，同时保留一套"契约测试"定期打真实沙箱，防止厂商悄悄改接口。
- 异步任务测试：提交 → 轮询 → 成功/失败/超时三种终态都要覆盖，特别是**超时后原图是否仍被删除**。

## 4. 端到端关键链路

| # | 链路 | 断言要点 |
| --- | --- | --- |
| E1 | 注册 → 同意 → 拍照建模 → 查看围度 | 同意记录落库；原图 1 小时内消失；围度密文存储 |
| E2 | 拒绝拍照同意 → 手动建档 → 获得推荐 | 不同意也能用，功能不被绑架 |
| E3 | 粘贴链接 → 解析成功 → 推荐 → 试穿 → 采纳 | 埋点齐全，指标可算 |
| E4 | 解析失败 → 手动录入尺码表 → 推荐 | 兜底路径可用 |
| E5 | 所有码都不合适 → 展示"不建议购买" + 定制入口 | 敢说别买；定制入口埋点上报 |
| E6 | 低置信度建模 → 提示复核 → 用户校正 → 推荐更新 | 校正后推荐缓存失效并重算 |
| E7 | 删除身体数据 → 模型资产与围度全部清除 | 资产 URL 失效 |
| E8 | 注销账号 → 冷静期 → 彻底清除 | 含备份清除任务入列 |
| E9 | 后台审核尺码表 → 发布 → C 端推荐结果变化 | 端到端配置生效 |
| E10 | 后台灰度松量规则 → 10% 用户命中新规则 | 哈希分桶稳定 |
| E11 | 量体 SDK 熔断 → 自动降级手动建档 | 降级提示友好，不白屏 |
| E12 | 后台查看身体数据明文 → 审批 → 审计留痕 | 无审批不可见；日志完整 |

E7、E8、E12 属于**合规链路**，建议纳入每次发布的强制回归，不可因赶工跳过。

## 5. 算法质量评测（本项目的特色重点）

### 5.1 三个黄金集

| 黄金集 | 规模 | 构建方式 | 用途 |
| --- | --- | --- | --- |
| 量体标定集 | ≥200 人 | 专业量体师软尺实测 + 标准化拍照，每人测两遍取均值 | 供应商选型验收、建模回归 |
| 尺码表标注集 | ≥1000 张 | 人工标注真值（含平铺/围量口径标记） | OCR 与归一化回归 |
| 推荐回放集 | ≥2000 条 | 有明确合身反馈的历史订单 | 规则变更回归 |

三个集合都**版本化入库**，与代码一样做变更管理。随着业务推进持续扩充，特别要补充**特殊体型样本**（BMI>28、BMI<18、腰臀差大、高个、矮个），因为这些人群误差最大且是高价值用户。

### 5.2 回归门槛（CI 中硬卡）

| 指标 | 阻断阈值 |
| --- | --- |
| 胸/腰/臀 MAE | 相比基线劣化 >0.2cm |
| 长度类 MAE | 劣化 >0.2cm |
| 任一 BMI 分段的 MAE | 劣化 >0.4cm（防止整体不变但某人群变差） |
| OCR 字段准确率 | 劣化 >1% |
| 平铺/围量判定准确率 | 劣化 >0.5%（判错代价极大） |
| 推荐一致率 | 劣化 >2% |

> 第三行很关键：**整体指标可能掩盖特定人群的退化**。只看总均值，很容易做出"对标准身材更准、对胖体更差"的优化，而后者恰恰是产品的核心用户。

### 5.3 置信度校准检验

按置信度分桶（0.5-0.6、0.6-0.7…0.9-1.0），统计每桶的实际正确率，画校准曲线。**要求单调递增**，否则说明置信度是装饰品。每月检查一次。

## 6. 性能测试

| 场景 | 目标 | 方法 |
| --- | --- | --- |
| 推荐接口 | 200 QPS，P95 <800ms，错误率 <0.1% | 压测（含缓存命中与未命中两种配比） |
| 商品解析 | 50 QPS，P95 <5s | 含 OCR 链路 |
| 建模任务 | 100 并发任务，队列等待 <3 分钟 | 长时压测，观察 GPU 扩缩容 |
| 数据库 | 主从延迟 <1s | 配合压测观察 |
| App 3D 渲染 | 中端机 ≥30 FPS，高端 ≥60 FPS | 真机实测，见 7.1 机型矩阵 |
| App 冷启动 | ≤2s | 真机实测 |

稳定性：**7×24 小时持续压测一轮**，观察内存泄漏与连接池耗尽——异步任务型系统最容易在长跑中暴露资源泄漏。

## 9. 测试数据管理

**严禁将生产数据同步到任何非生产环境**（文档 06 第 5.3 节）。测试数据全部由合成数据生成器产出：

- 人体数据：按国标人体尺寸分布（GB/T 1335、GB/T 10000）采样生成，覆盖各体型段。
- 尺码表：从公开商品结构中抽象出模板后随机生成，含刻意注入的脏数据（缺字段、单位错误、非单调）。
- 用户行为：脚本模拟完整链路。

黄金集中的真实人体数据属于敏感信息，须**单独存储、加密、访问审批**，不得进入普通测试环境。

## 10. 质量门禁与缺陷管理

### 缺陷分级

| 级别 | 定义 | 修复时限 |
| --- | --- | --- |
| P0 致命 | 崩溃、数据泄露、资金损失、核心链路不可用 | 立即，不修不发 |
| P1 严重 | 主功能异常、推荐结果明显错误、合规缺陷 | 发布前必修 |
| P2 一般 | 次要功能异常、体验问题 | 本迭代 |
| P3 轻微 | 文案、样式 | 排期 |

**推荐结果错误按 P1 处理**，即使它不导致崩溃。用户对"给了错误建议"的容忍度远低于"功能有点卡"。

### 准入准出

- **提测准入**：自测通过、单测达标、接口文档更新、涉及配置的变更已说明。
- **发布准出**：P0/P1 清零、回归通过、黄金集回归通过、性能达标、安全扫描通过、《07 文档》第 8 章上线清单全绿。

## 11. 内测阶段的特殊质量活动

MVP 要做 500–2000 人内测，这是最有价值的质量数据来源，需要专门设计：

1. **建模精度众测**：邀请内测用户自报软尺实测值（提供量体教程视频），与系统输出比对，快速扩充标定集。给予奖励激励参与。
2. **推荐结果追踪**：对每一次采纳推荐的购买做收货回访，形成推荐回放集。
3. **流失漏斗分析**：重点看建模流程各步骤的流失率，尤其是"隐私同意页"和"拍照页"两处——这两处的流失率决定产品能否成立。
4. **定性访谈**：每周访谈 5 位用户，问题聚焦"你信不信这个推荐""你为什么没拍照"。定量数据告诉你哪里流失，定性访谈才告诉你为什么。
