# 06 · 安全与合规设计

> **本文档是本项目的最高优先级文档之一。** 人体照片与体型围度属于敏感个人信息，一次泄露事故足以终结整个产品。
> **后续一切技术开发的前置条件**：必须保护客户隐私安全，遵守下列法规。功能与隐私冲突时，停功能，不补票上线。
> 适用法规：《个人信息保护法》《数据安全法》《网络安全法》《App 违法违规收集使用个人信息行为认定方法》；若采集人脸，还适用《人脸识别技术应用安全管理规定》（本产品默认不采人脸）。
> 关联：PRD 5.2、《02-数据库设计》第 5 章、《03-API接口设计规范》第 3.3 节、《10》3.1 / 4.5、仓内 `.cursor/rules/privacy-legal.mdc`

## 1. 合规定位：我们在处理什么级别的数据

| 数据 | 分级 | 依据 |
| --- | --- | --- |
| 人体全身照片 | **敏感个人信息** | 可关联生物特征、体貌，泄露易致人格尊严受损 |
| 身体围度（胸/腰/臀等） | **敏感个人信息** | 属于健康生理信息范畴，且高度私密 |
| 3D 人体模型 | **敏感个人信息** | 由上述数据生成，同等对待 |
| 手机号 | 个人信息 | 仅登录/找回，密文；界面不展示完整号码 |
| 真实姓名、身份证 | **不采集** | C 端无法律必要；禁止入库 |
| 购物与推荐记录 | 个人信息 | |
| 设备与日志 | 个人信息（去标识后可降级） | |

**结论**：本产品核心业务就建立在敏感个人信息之上，因此必须满足 PIPL 对敏感信息的加严要求——单独同意、特定目的、充分必要、严格保护措施、事前个人信息保护影响评估（PIA）。

## 2. 十条安全基线（不可妥协）

1. **原始照片生命周期 ≤ 1 小时**，建模完成即删，桶生命周期兜底，删除动作写审计。
2. **默认不采集人脸**，模型形象使用无面部特征的人台；若拍摄照片含面部，端侧在上传前即做模糊/裁切处理。
3. **单独同意**：人体数据处理的同意必须是独立弹窗、独立勾选、独立记录，不得与《用户协议》合并勾选，不得默认勾选。
4. **围度字段级加密**：AES-256-GCM，密钥托管 KMS，业务库中是密文。数据库被拖走也拿不到明文。
5. **端侧优先**：姿态检测、构图判断、人脸模糊全部端侧完成，画面不上传。
6. **最小化**：C 端不采集真实姓名、身份证、证件照、人脸核身；只存生日年份不存完整生日；不采集通讯录、位置、相册全量权限（只用相机当场拍或单张选取）。`users` 表禁止增加 `real_name` / `id_card` 一类字段。
7. **访问必审计**：任何对身体数据的读取（含后台、含运维、含算法调试）都留痕，日志独立存储且运维无删除权。
8. **明文查看需审批**：后台默认脱敏，明文需工单 + 审批 + 时限 + 水印。
9. **第三方约束**：量体 SDK 供应商须签 DPA，明确不得留存、不得用于其训练、不得境外传输，违约赔偿条款入合同。
10. **可删除可注销**：用户随时可删身体数据；注销后 T+15 日内彻底清除，**含备份**。

## 3. 同意管理设计

### 3.1 同意场景拆分

| 场景 key | 说明 | 是否必需 |
| --- | --- | --- |
| `basic_service` | 基础服务（账号、浏览） | 必需 |
| `body_photo` | 拍照建模（处理人体照片） | **单独同意**，不同意可用手动建档 |
| `body_data_train` | 将脱敏体型数据用于算法改进 | **单独同意**，可拒绝且不影响功能 |
| `third_party_measure` | 数据交由指定第三方量体服务处理 | **单独同意**，须列明供应商名称 |
| `marketing_push` | 营销推送 | 可选 |

**关键设计**：`body_photo` 与 `body_data_train` 必须分开。把"用你的数据训练我们的模型"藏在建模同意里，是典型的违规做法，也是监管通报的高发点。

### 3.2 同意的技术实现

- 每次同意写入 `consents` 表：用户、场景、政策版本、时间、IP、设备。
- 隐私政策变更且涉及敏感信息处理范围时，**必须重新取得同意**，旧同意失效。
- 建模接口强校验 `consent_id`，无有效同意直接返回 `40301`。
- 撤回同意的入口与授予同意同样显眼；撤回后停止相应处理，已有数据按用户选择保留或删除。

## 4. 数据保护技术方案

### 4.1 存储

```
原始照片   → raw-photo-bucket（独立桶）
             · 服务端签名直传，客户端不经业务服务器
             · 桶策略：禁止公共读、禁止列举、启用服务端加密
             · 生命周期规则：1 小时自动删除（兜底）
             · 任务完成即主动删除并记录 photo_purged_at

3D 模型    → assets-bucket
             · 访问一律用 10 分钟有效期的签名 URL
             · key 含随机盐，不可枚举

围度数据   → PostgreSQL · BYTEA 密文（应用层 AES-256-GCM）
             · 数据密钥 DEK 由 KMS 主密钥 KEK 包裹，定期轮换
             · 置信度等非敏感字段明文存，便于统计

审计日志   → 独立库/独立权限，只追加，按月分区，保留 ≥3 年
```

### 4.2 传输

TLS 1.3；App 侧 SSL Pinning；内部服务间 mTLS；签名 URL 短时效；敏感接口禁止 GET 带参（防日志与 Referer 泄露）。

### 4.3 密钥管理

| 密钥 | 存放 | 轮换 |
| --- | --- | --- |
| 字段加密 KEK | 云 KMS，人工不可导出 | 年度 |
| DEK | 密文存配置，运行时解包 | 季度 |
| JWT 签名私钥 | KMS / 密钥管理服务 | 季度，支持双密钥并行过渡 |
| 第三方 SDK 凭证 | 密钥管理服务，不进代码仓库 | 按厂商要求 |

**红线**：任何密钥、Token、数据库口令出现在 Git 仓库中，即视为安全事故，须立即轮换。CI 中加 secret 扫描（如 gitleaks）阻断提交。

## 5. 访问控制

### 5.1 后台四道门

```
1. 网络：仅内网/VPN 可达，公网无 DNS 解析
2. 身份：账号密码（argon2id）+ 强制 MFA + IP 白名单
3. 授权：RBAC 权限点，最小权限；身体数据权限单独授予且默认无人拥有
4. 审计：全操作留痕；敏感操作需二次审批
```

### 5.2 角色与敏感数据权限矩阵

| 角色 | 身体数据 | 用户手机号 | 规则发布 | 数据导出 |
| --- | --- | --- | --- | --- |
| 超级管理员 | 脱敏（明文需审批） | 脱敏 | ✓ | 需审批 |
| 运营 | ✗ | ✗ | ✗ | ✗ |
| 审核员 | ✗ | ✗ | ✗ | ✗ |
| 算法工程师 | **去标识化聚合数据** | ✗ | ✗ | 需审批 |
| 客服 | 脱敏，仅限有工单关联的用户 | 后四位 | ✗ | ✗ |
| 财务 | ✗ | ✗ | ✗ | ✗ |

> 注意算法工程师这一行：他们需要数据做优化，但需要的是**去标识化的聚合数据集**，而不是能定位到具体某个人的原始记录。区分这两者是合规设计的基本功。

### 5.3 生产环境访问

- 开发人员默认无生产数据库权限；临时授权走审批，有效期 ≤4 小时，全程录屏或命令审计。
- 严禁把生产数据同步到测试环境。测试数据一律用**合成数据生成器**（见文档 08）。

## 6. 用户权利实现

| 权利 | 实现 | 时限 |
| --- | --- | --- |
| 知情权 | 隐私政策 + 弹窗说明 + 第三方 SDK 清单公示 | 实时 |
| 查阅权 | App 内查看全部身体数据与推荐历史 | 实时 |
| 复制权 | 申请导出个人数据副本（结构化文件） | 15 日内 |
| 更正权 | 围度可手动修改 | 实时 |
| 删除权 | 删除单个档案 / 删除全部身体数据 | 实时生效，备份 T+15 清除 |
| 撤回同意 | 设置页一键撤回 | 实时 |
| 注销 | 二次验证 + 7 日冷静期 + 彻底清除 | T+15 完成 |
| 解释权 | 推荐结果可查看依据（`explain` 字段） | 实时 |

**注销清除的技术难点是备份**。方案：备份加密存储，注销名单写入"待清除表"，每次备份恢复演练与过期备份轮转时执行清除；承诺周期设为 T+15 而非 T+3，就是为了覆盖备份轮转周期。**承诺做不到的时限，比不承诺更危险。**

## 7. 第三方 SDK 治理

| 要求 | 说明 |
| --- | --- |
| SDK 清单公示 | App 内可查，列明名称、公司、用途、收集信息、隐私政策链接 |
| 最小权限 | SDK 不得自行申请权限，不得在用户同意前初始化 |
| 延迟初始化 | 所有 SDK 在用户同意隐私政策后才初始化（这是应用商店合规审核的必查项） |
| 数据处理协议 | 量体 SDK 必签 DPA：不留存、不训练、不出境、可审计 |
| 定期审计 | 每季度抓包核查 SDK 实际网络行为，与声明比对 |
| 应急替换 | 供应商出现合规问题时，能在 24 小时内切换（靠 J-9 的流量配置） |

## 8. 应用安全

| 面向 | 措施 |
| --- | --- |
| 接口 | 鉴权、限流、幂等、参数校验、防重放（时间戳+nonce） |
| 越权 | 所有资源访问校验归属（`profile.user_id == token.user_id`），**IDOR 是这类产品最容易出的漏洞** |
| 注入 | 参数化查询，禁止拼接 SQL |
| 上传 | 类型与大小校验、图片重编码去除 EXIF（**EXIF 含 GPS，必须剥离**） |
| 爬虫与刷量 | 设备指纹、行为风控、建模次数限制（也是成本保护） |
| 依赖 | SCA 扫描，高危漏洞 48 小时内修复 |
| 客户端 | 代码混淆、反调试、SSL Pinning、后台模糊遮罩 |

## 10. 安全事件应急预案

```
发现（监控告警 / 用户举报 / 外部通报）
  ↓ 15 分钟内
定级：P0 数据泄露 · P1 越权访问 · P2 漏洞未利用 · P3 一般
  ↓
遏制：下线受影响接口、吊销密钥与 Token、阻断异常账号
  ↓
取证：保全日志与审计记录（禁止清理现场）
  ↓
评估影响范围：涉及多少用户、哪些字段
  ↓ P0/P1
通报：依法向监管部门报告，并逐一告知受影响用户
  ↓
修复与复盘：根因分析、修复验证、制度改进，7 日内出报告
```

**关键纪律**：数据泄露必须依法告知用户，不得隐瞒。隐瞒带来的后果远大于泄露本身。

## 11. 隐私即卖点

最后一点是产品视角的：这个产品要求用户上传全身照片，**心理门槛是转化漏斗上最大的一道坎**。与其把合规当成成本，不如把它做成营销素材：

- 建模页明确写"照片仅用于生成模型，处理完成后 1 小时内自动删除，我们不保存你的照片"。
- 姿态检测在手机本地完成，可以直接说"取景画面不会离开你的手机"。
- 用无面部人台，告诉用户"我们不需要你的脸"。
- 提供"不想拍照？用身高体重先建弱档"的平行路径（厘米数手填不是默认替代，见《10》4.2 / 4.5）。

这些话术必须与技术实现完全一致——**说了做不到就是虚假宣传**，风险比不说还大。C 端采集、着装、原图短删与客户口径的完整记录见《10-C端信息架构与自有人体模型》第 4.2～4.5 节。
