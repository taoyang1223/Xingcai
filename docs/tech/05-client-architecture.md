# 第一部分：移动 App

## 1. 技术栈与分层

**主体 Flutter 3.24 + 原生插件**（ADR-05 已锁定，见《00 技术路线》）。

状态管理锁定 **Riverpod**，不混用 Bloc / GetX。

选择理由与代价：三端并行、客户端人力有限，跨端省约 40% 工作量；代价是相机、3D、量体 SDK 必须走 Platform Channel。若采购 SDK 无法封装到 Flutter，**优先换供应商，不推翻 App 框架**。

```
lib/
├── app/                  # 入口、路由、主题、全局 Provider
├── core/                 # 基础设施
│   ├── network/          # Dio 封装：拦截器、Token 刷新、重试、trace_id
│   ├── storage/          # 安全存储（Keychain/Keystore）、本地缓存
│   ├── error/            # 统一错误类型与降级策略映射
│   ├── analytics/        # 埋点
│   └── config/           # 远程配置与 Feature Flag
├── data/                 # 数据层
│   ├── api/              # 由 OpenAPI 自动生成，禁止手改
│   ├── models/           # DTO
│   └── repositories/     # 仓储实现（网络+缓存策略）
├── domain/               # 领域层：实体、用例、仓储接口
├── features/             # 按业务特性组织
│   ├── auth/
│   ├── onboarding/       # 隐私同意、引导
│   ├── body/             # 建模、拍照引导、围度校正
│   ├── catalog/          # 商品解析、尺码表
│   ├── recommend/        # 推荐结果、部位诊断
│   ├── tryon/            # 3D 试穿（内含原生 View 桥接）
│   ├── feedback/
│   └── profile/
└── native/               # Platform Channel 定义
    ├── camera_guide/     # 拍摄引导（原生相机 + 姿态检测叠加层）
    ├── measure_sdk/      # 量体 SDK 桥接（对应服务端 MeasureProvider 的端侧版本）
    └── renderer_3d/      # 3D 渲染 PlatformView
```

约束：UI 层不直接调 repository，一律经过 usecase；异步状态用统一的 `AsyncValue` 三态（loading/data/error），避免每个页面各写一套加载与错误处理。

## 2. 三个技术难点的实现要点

### 2.1 拍摄引导（决定建模成功率的关键 UI）

用户拍照姿势不对，再好的算法也白搭。拍摄引导要做的是**在拍之前就把照片质量卡住**：

```
实时检测（端侧轻量姿态模型，如 MediaPipe Pose，不上传）
  ├─ 人体是否完整入框（头顶与脚部都在框内）
  ├─ 距离是否合适（人体高度占画幅 70%~85%）
  ├─ 手机是否垂直（陀螺仪判定，倾斜 >5° 提示）
  ├─ 姿势是否正确（A-Pose：双臂张开约 45°，双脚分开与肩同宽）
  ├─ 光线是否充足（亮度直方图）
  └─ 背景是否过于杂乱（可选，弱提示）
全部满足 → 自动倒计时 3 秒拍摄（用户不用够快门键，避免姿势变形）
```

这些检测**全部在端侧完成，画面不上传**。这既是合规要求，也是可以直接写进隐私说明打消用户顾虑的卖点。

引导文案要具体："请把手机靠墙立稳" 比 "请保持手机稳定" 有用得多。

### 2.2 3D 渲染桥接

Flutter 通过 `PlatformView` 嵌入原生渲染视图：iOS 用 SceneKit/Metal，Android 用 Filament。二者共用同一套 glTF 资源与同一套热力图着色器逻辑（GLSL/MSL 两份实现，但算法一致）。

性能纪律：

- 模型走 Draco 压缩，单模型 ≤3MB；首次下载后本地缓存，按 `profile_version` 失效。
- PlatformView 在页面不可见时必须暂停渲染循环，否则后台耗电投诉会很快到来。
- 设备分档（文档 04 第 4.3 节）在 App 启动时测一次并缓存，不要每次进页面重测。

### 2.3 建模任务的等待体验

建模要 20–30 秒，这段时间是流失高发区：

- 提交后立刻进入结果页骨架屏，展示**分阶段进度**（"上传完成 → 识别体型 → 计算围度 → 生成模型"），而不是一个转圈。
- 用 WebSocket 或长轮询（首选服务端推送，降级为 2 秒轮询）。
- 等待期间穿插科普内容（"你知道吗：同样标 L 码的衬衫，胸围可能相差 6cm"），既填充时间又强化产品价值。
- 超过 45 秒未完成，主动提供"先用身高体重快速建档"的出口，**不要让用户干等到超时**。

## 3. 离线与缓存

| 数据 | 策略 |
| --- | --- |
| 身体档案与围度 | 本地加密缓存（Keychain/EncryptedSharedPreferences），支持离线查看 |
| 3D 模型文件 | 文件缓存，LRU，上限 100MB |
| 商品与推荐历史 | 缓存最近 50 条，离线可看 |
| 配置与 Feature Flag | 启动拉取 + 本地兜底默认值 |

**绝不缓存**：原始照片（用完即删）、Token 明文（走安全存储）。

## 4. 安全要点（客户端侧）

- 证书校验（SSL Pinning），防中间人抓包。
- 越狱/Root 检测，敏感操作时提示风险（不强制阻断，避免误伤）。
- 应用切后台时对含身体数据的页面加**模糊遮罩**（多任务截图防窥）。
- 截图检测：查看围度详情页时若检测到截图，提示"含个人敏感信息，请谨慎分享"。
- 分享出去的试穿图**必须剥离围度数字**，只保留视觉效果（PRD E-8）。
- 埋点数据不得包含任何围度数值。

## 5. 包体与启动性能

| 指标 | 目标 |
| --- | --- |
| 安装包大小 | Android ≤ 60MB、iOS ≤ 80MB（3D 引擎是大头，模板资源走动态下载） |
| 冷启动 | ≤ 2s（中端机） |
| 首页可交互 | ≤ 2.5s |
| 崩溃率 | ≤ 0.2% |

服装模板网格、示例资源一律**动态下发**，不打进包体。

# 第二部分：Web 后台管理系统

## 6. 技术栈

React 18 + TypeScript 5 + Vite + Ant Design Pro + TanStack Query + Zustand。

不自研组件库，不追求视觉创新。后台的价值是**让审核员每天能多处理 200 条尺码表**，一切设计围绕操作效率。

```
src/
├── api/            # OpenAPI 自动生成 + TanStack Query hooks
├── components/     # 业务通用组件（审核工作台、尺码表编辑器、规则编辑器）
├── layouts/        # 布局与菜单（按权限动态生成）
├── pages/
│   ├── review/     # 审核队列（最高频页面，单独优化）
│   ├── catalog/    # 商品与尺码表
│   ├── config/     # 品类模板、松量规则、开关
│   ├── users/      # 用户与身体档案（脱敏）
│   ├── providers/  # 量体 SDK 供应商管理与 A/B
│   ├── dashboard/  # 监控看板
│   ├── tickets/    # 工单
│   └── audit/      # 审计日志
├── auth/           # 登录、MFA、权限判断
└── utils/
```

## 7. 权限体系落地

前端做**菜单与按钮级**控制，服务端做**接口与数据级**控制，两层缺一不可（前端权限只是体验优化，绝不能当作安全边界）。

```tsx
// 权限判断统一走一个 hook，禁止在业务代码里散落 role === 'admin' 这类判断
const canPublish = usePermission('config:rule:publish');
```

菜单按权限点动态生成；无权限页面直接 403 而非渲染空白。

## 8. 三个核心页面的交互设计要点

### 8.1 尺码表审核工作台（决定运营效率的页面）

左右分栏：左侧原图（可缩放、可框选），右侧 OCR 结果表格（可编辑）。要点：

- **低置信度单元格高亮标红**，审核员只需要看红的，不用逐格核对。
- 键盘流：`Tab` 切单元格、`Enter` 提交并自动加载下一条、`Esc` 跳过。审核是重复劳动，鼠标操作会拖垮效率。
- 一键"平铺↔围量"切换（全表 ×2 或 ÷2），这是最高频的修正动作。
- 提交后显示"本条修正了 3 处"，数据回流给 OCR 训练。
- 队列支持按品类/优先级筛选，让审核员形成手感（连续审同品类速度更快）。

### 8.2 松量规则编辑器

规则是四维的（品类 × 版型 × 弹性 × 部位），纯表格很难看懂。设计要点：

- 以"品类 + 版型"为一个卡片，卡片内用**可视化区间条**展示 min/ideal/max，拖拽调整。
- 修改后立即用**历史真实数据回放**预览影响："此改动将使 1,247 条历史推荐中的 83 条结论发生变化"——这是防止误操作的最后一道防线。
- 保存为草稿 → 提交审核 → 灰度 10% → 观察 3 天 → 全量。每步都有明确按钮和状态。
- 必须支持一键回滚到上一版本。

### 8.3 身体档案查询（合规重点页面）

- 默认全部脱敏（`9x.x`），页面顶部常驻醒目提示"本页含敏感个人信息，所有操作已记录"。
- 查看明文需填写工单号与理由并提交审批，审批通过后开放 15 分钟窗口。
- 明文展示时叠加**含操作人工号的水印**（防截图外传）。
- 禁用批量查询与导出按钮（导出走单独的审批流）。

## 9. 前端工程约束

- 大表格统一用虚拟滚动，单页渲染上限 100 行。
- 所有列表页的筛选条件写入 URL query，支持刷新保持与链接分享（运营之间传递问题现场全靠这个）。
- 统一错误处理：40301 跳授权、40302 提示无权限、5xx 展示 trace_id 方便报障。
- 构建产物 gzip 后首屏 ≤ 500KB，路由级代码分割。

# 第三部分：三端共用约定

| 事项 | 约定 |
| --- | --- |
| 接口层代码 | 全部由 OpenAPI 生成，禁止手写 DTO |
| 错误码处理 | 共用一份错误码到文案、到降级动作的映射表，由服务端下发可覆盖 |
| 埋点事件 | 统一事件字典（`事件名 + 参数 schema`），新增事件需登记；禁止上报围度数值 |
| 设计规范 | 共用 Design Token（颜色、间距、字号），热力图配色三端严格一致 |
| 时间与单位 | 一律 UTC 传输、本地展示；尺寸一律 cm 保留一位小数 |
| 版本兼容 | 服务端至少兼容最近 2 个 App 大版本；强更走 `/common/config` |
| 国际化 | MVP 只做中文，但文案不硬编码，全部走资源文件（尺码体系天然有多国需求） |

## 10. 客户端埋点关键事件（决定能否验证 PRD 指标）

| 事件 | 关键参数 | 支撑的指标 |
| --- | --- | --- |
| `onboarding_consent_result` | scene, granted | 授权转化率 |
| `body_modeling_start/step/finish` | source, step, duration, fail_reason | **建模完成率**（北极星指标的分母） |
| `body_measure_corrected` | part, delta（只传差值不传原值） | 用户校正率 |
| `catalog_parse_result` | status, category, confidence | 解析成功率 |
| `recommend_view` | record_uid, confidence, risk | — |
| `recommend_adopt` | record_uid, size | **推荐采纳率** |
| `tryon_render` | device_tier, fps, duration | 渲染性能与降级比例 |
| `custom_entry_click` | source_page | **二期定制需求验证**（PRD 第七章要的那个数字） |
| `feedback_submit` | overall_fit, returned | 退货率与闭环 |

> 埋点要在开发阶段就和指标定义对齐。上线后才发现"算不出建模完成率"，是最常见也最浪费时间的返工。
