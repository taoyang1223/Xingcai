## 1. 一句话与当期验证

**产品（长期）**：客户用一部手机建起带真实尺寸的人体模型，用来选对现成衣服的尺码、预览穿着。定制与制版后移。

**当期只验证这一条假设**：用户愿意为更准的尺码建议，完成一次建档（先弱档、后拍照），并看懂「推荐码 + 部位诊断」。

每天打开只干一件事：**这件衣服，我穿哪个码。**  
登录解决「是同一个人」；人台解决「体型」；隐私解决「敢拍」。三者都不替代选码。

四条硬约束（与功能冲突时停功能）：

1. **方便**：主路径不填 22 个厘米数；一个人、靠墙、倒计时拍正侧两张 + 身高。
2. **精准**：胸腰臀 MAE ≤ 2cm 是拍照建档的验收线，不是弱档的验收线。
3. **可信**：缺侧面、穿卫衣、测不准必须示弱或拦截，禁止假装很准。
4. **合法**：单独同意、围度加密、原图不进业务库、C 端不采真名/身份证。

## 2. 主流程（给设计画稿用）

```
打开 → 登录（伪匿名）
  → 首页人台三态之一（见 §3）
      空态：主按钮 = 拍照建档；弱档入口次之；粘贴链接禁用
      弱档：可手填尺码表看推荐；首页标明「建议拍照」；粘贴链接「尚未开通」
      准档：仍用手填尺码表看码（阶段 1～2）；粘贴链接待 8.2 后半
  → 推荐结果：主码 + 备选 + 部位诊断 + 置信度（见 §5）
  → 都不合适：只埋「想定制一件？」点击，不做下单
```

底栏只四个坑：**首页 / 试穿 / 档案 / 我的**。不要商城、社区、消息。  
阶段 1 的「试穿」只作占位；可隔离验证 3D 人台展示，但不并入选码交付，阶段 4 才评审开放 3D 试穿。展示人台不等于照片量体、成衣试穿或纸样制版。

账号口径（已锁，评审不要再打开）：

- 微信 / 支付宝 / 手机号登录；展示名系统生成（可改昵称，文案不得写「真实姓名」）
- 禁止：身份证、证件照、人脸核身、通讯录、微信实名资料
- 手机号若采集：只作登录找回，HMAC + 密文，界面不展示完整号码

## 3. 首页三态（空 / 弱 / 准）

首页不是电商首页。只放：人台状态、一个主操作、最近推荐、隐私条。

| 状态 | 何时 | 人台 | 主按钮 | 粘贴链接 | 禁止出现 |
| --- | --- | --- | --- | --- | --- |
| **空态** | 无身体档案 | 通用头的展示角色（见《14》） | **拍照建档** | 禁用 | 胸腰臀三个数；「已建档」 |
| **弱档** | 仅身高体重（+ 体型模板）；未拍照或拍照未反解 | 人台可显示，完整度低 | 手填尺码表看码（阶段 1）；「拍照补测」并列 | 禁用（阶段 1～2 已定） | 把弱档写成「已测准」「推荐可用」而不加限制 |
| **准档** | 拍照反解完成，关键部位达推荐阈值 | 同一具展示角色 + 完整度如「18/22 已测 · 推荐可用」。头不随用户变化 | 手填尺码表看码；「拍照补测」 | 阶段 1～2 禁用；阶段 3 是否开放链接仍待 8.2 后半勾选 | 用胸围/腰围/臀围三个数代表整份档案 |

完整围度只在**档案页**。档案按字典分组，每行带状态：高 / 中 / 推算 / 已校正 / 缺失。  
缺失部位不参与对应品类打分。

隐私条长期挂首页底部：**「人体照片处理完即删，不留原图」。**

## 4. 建档三层（谁填什么）

人体字段以《02》附录 A 现有 22 项可测 key（cm）为基线；新增字段须单独评审，不因 3D 能画出来就视为测准。三份合同禁止混用：

- **人体净体合同**：部位/解剖标志点、测量路径、单位与左右侧、档案版本；每项记录来源（实测/用户校正/照片反解/弱档推算）、部位置信度及缺失状态。弱档推算不得冒充实测；围度和模型参数按《06》密文存储、按归属授权读取。
- **衣服成衣合同**：商品/尺码表版本、品类与码名、衣长/袖长/平铺胸宽等成衣实物尺寸、测量方式（平铺半宽或围量）、单位、来源及审核状态；买家适穿身高/胸围区间只是**适用人体范围**，不是衣服实测尺寸。未知口径不做 ×2 猜测，不参与该部位推荐。
- **纸样合同**：未来制版专用，版片线/缝合线、缝份、对位点、丝缕方向、面料缩率、号型和修订版；纸片尺寸不是成衣净尺寸，更不是人体净体。只有经纸样→裁剪缝制→成衣复测的转换及实物验收，才能声称可生产。`tools/blender/` 里的合成 T 恤几何只用于离线复测，不是本阶段产品交付，不可打印投产。

上身、下身及手/脚若新增 key：先定义部位边界、左右侧、净体/成衣归属、单位与采集方法；按品类验证缺失/异常/左右不对称、测量算子与软尺参照误差及不同体型分层置信度，再升级字典/接口/规则版本和回归用例。手脚无法可靠采集时保持缺失，不从网格外观或上/下身推算后宣称实测；未经阶段评审不扩大推荐品类。

| 层 | 客户做什么 | 系统做什么 | 置信度 | 哪一阶段做 |
| --- | --- | --- | --- | --- |
| **主路径** | 换贴身衣 → 手机靠墙 → 走进人台框 → 倒计时拍正面 → 转 90° 拍侧面；只填身高（体重可选） | 端侧拦截废片/裸露/卫衣；糊脸后才考虑上传；反解 \(\beta\)，切出 22 项 | 按部位给 | **阶段 2** |
| **弱档** | 身高、体重（可缺）、体型模板（女/男/中性）；捏人采集意向见 8.6，受 8.7 门禁约束 | 统计体型先用着，能出低置信推荐 | 封顶；首页写「建议拍照」 | **阶段 1**先完成无需 3D 的输入与选码 |
| **校正** | 获批后可看展示人台拖肚子/肩宽，或事后点「这件偏紧/刚好/偏松」 | 改的是模型参数，不是让客户回忆厘米数 | 记入已校正（不等于实测） | 滑杆须过 8.7 展示门禁；穿着反馈在阶段 4 |
| **高级手填厘米** | 档案页折叠入口，给极少数知道自己围度的人 | 写入须带同意；改一处，相关围度与人台一起动 | 已校正 | 阶段 1 可先做**内部/高级**入口，**不得**做成登录后默认引导 |

**禁止**：把「请填写胸围腰围」当建档主流程；把身高体重标成准档案；假设旁边有人按快门；引导裸体或仅内衣。

着装（阶段 2 文案已定）：穿贴身短袖/运动背心 + 紧身裤或薄打底。禁止羽绒服、宽松卫衣、遮腰连衣裙。不拍裸体。

## 5. 尺码从哪来、推荐长什么样

### 5.1 商品入口（分阶段打开）

| 入口 | 阶段 1～2 | 阶段 3 | 永不下线 |
| --- | --- | --- | --- |
| 手填尺码表 | **唯一可用** | 解析失败时的退路 | 是 |
| 尺码表截图 OCR | 不做 | 计划做（不依赖开放平台）；低置信进人工队列 | — |
| 粘贴淘宝链接 / 分享 | 界面可露，点击「尚未开通」 | **仍未拍板**（8.2 后半：分享+OCR 或官方 API） | — |

禁止：大规模爬虫。无论阶段 3 怎么勾，手填都不下线。

平铺 vs 围量：尺码表「胸围」可能是成衣平铺半宽、成衣围量，也可能是适穿**人体围度**；先确认字段对象、单位和测量路径，只有确认平铺半宽才 ×2。存疑则该部位不参与推荐。手填也要记录来源和复核状态，不能因「手填」就标为商家实测。

开发环境原型（未获阶段 0 批准，不对真实用户开放）：只有用户手填的对应围度参与规则，身高、体重和体型模板不换算成围度。成衣围度相对人体围度落在未经验证的品类松量带之外时，不返回主码。尺码表的平铺或围量由调用方声明，结果必须标明未经复核。

第一期品类模板只配 3 个：**T恤/卫衣、衬衫、裤装**。其余品类不做，或只展示已有部位并标低置信（阶段 1 建议直接不做）。商家商品/尺码表接入是后期独立门禁：需核验商家身份、商品数据使用及展示授权、来源/更新/撤回范围和权限隔离；用户手填或上传截图不等于商家授权，更不能开启商家后台、批量抓取、SDK 或访问用户身体明文。商家只接收明确授权且最小必要的推荐结论，未经用户另行同意不接收净体尺寸、照片或可识别模型。

### 5.2 推荐结论（C 端必须能读完）

推荐引擎第一期是**规则**，不是模型。松量在配置表，改规则不发版。每条推荐打快照：身体版本 + 尺码表版本 + 规则版本。

C 端一张结果页只含：

| 块 | 内容 | 弱档时 |
| --- | --- | --- |
| 主推荐 | 码名（如 L） | 必须带「仅供参考，建议拍照后更准」 |
| 备选 | 至多 1 个 + 一句为何备选 | 可空 |
| 置信度 | 高 / 中 / 低，禁止只给一个百分数假装精确 | 封顶为低或中低 |
| 部位诊断 | 逐部位：合适 / 偏紧 / 偏松 / 可能短；**缺测部位明确写「未测，未参与」** | 只基于身高体重推算的部位必须标明 |
| 不敢买 | 肩宽或裤腰硬约束触发时，主结论可以是「不建议买」+ 理由 | 同样适用 |
| 定制入口 | 「没有合适尺码？想定制一件？」仅埋点 | 阶段 1 就可埋，不做履约 |

**禁止**：没有部位说明的光秃秃一个码；把推算值写成实测；分享卡片上出现围度数字。

## 6. 同意与隐私（功能可砍，这条不能砍）

写身体数据前必须有有效 `consent_id`，否则拒绝（`40301`）。场景拆开勾，禁止塞进一份用户协议。

| 场景 key | 何时出现 | 拒绝的后果 |
| --- | --- | --- |
| `basic_service` | 注册/登录 | 不能用账号 |
| `body_data` | 任何身体档案写入（含弱档身高体重） | 不能建档、不能推荐；仍可浏览壳 |
| `body_photo` | 进入拍照前 | 不能拍照；必须仍能走弱档 |
| `body_data_train` | 独立勾，默认关 | 不影响选码；不得拿原图或可识别体型去训练 |
| `third_party_measure` | 仅当照片/数据要出我方环境给厂商时 | 不能走该厂商；可走纯本地/手填 |
| `marketing_push` | 可选 | 不影响功能 |

说明：`body_data` 是本文相对《06》的补全——弱档也会写入敏感个人信息，不能只在拍照时才同意。评审通过后写入《06》。

其它已锁基线（不展开）：围度只走统一加解密、业务库密文；照片端侧糊脸与拦截 → 短存桶直传 → 建模完即删（≤1 小时兜底）；业务库不存原图；日志不得出现围度数字、照片 URL、完整手机号；C 端 `users` 不加 `real_name` / `id_card`；未成年人第一期不提供拍照建档。

### 阶段 1 · 选码内核（下一件研发）

验证「规则能不能给出可信码」。没有它，拍照无法验收。

| 端 | 功能 |
| --- | --- |
| 同意 | `basic_service` + `body_data`；无同意不能写档案 |
| 身体 | 弱档：身高、体重（可缺）、体型模板；高级校正入口可先开给内部 |
| 商品 | **仅手填尺码表**；字段归一到字典；平铺/围量判定 |
| 推荐 | 主码 + 备选 + 部位诊断 + 置信度；硬约束可「不建议买」；快照 |
| 配置 | T恤、衬衫、裤装的字段模板 + 松量规则（改配置能变推荐） |
| 后台 | 能编辑上述规则（可简陋）；审计最小集（谁改了规则） |
| C 端 | 登录已有；弱档 → 手填尺码表 → 结果页；粘贴链接禁用；拍照主按钮可露但进「尚未开通」或仅交互稿 |

完成定义：固定几套合成数据，改松量后推荐变化；低置信会说不确定；人体/成衣的对象、单位、来源和缺失边界可追溯。**先验收选码链，再评审展示实验**；选码不依赖 3D，展示故障不得阻断推荐。
不做：相机、糊脸、OSS、OCR、淘宝链接解析、3D **试穿/量体/制版的产品交付**、支付、厂商 SDK 真接。阶段 1 的 L2 仅可在产品负责人明确批准阶段 0 且单独确认技术路线、资源授权、真机降级后做隔离展示验证；未获批准不合入产品路径，不得占用或替代选码验收。

架构验收（对齐《00》五步，按本文解释）：创建的是**弱档/手动档案**（明文进接口、库内密文），不是让 C 端用户填 22 项。

| 层 | 做法 | 能捏 | 能转 | 排期 |
| --- | --- | --- | --- | --- |

| **L2 实时网格** | Web 壳获批时可评估 three.js + 低面数人体，滑杆驱动 morph target | 是 | 是 | **选码验收后隔离实验，须另批** |

**L2 实验前必须落实，缺一项不许进入产品路径**：

1. **模型来源与授权**：SMPL / SMPL-X 学术许可不得直接当商用许可；自制、MakeHuman 导出或采购资产均须逐项核验模型、贴图及衍生使用条款，授权证据留档后才可进入产品路径。此处不是已有授权证明。

#### 8.7.1 用什么渲染：先回答 C 端壳是什么（未决）

《10》第 1.2 节写的是 **Flutter 壳 + 原生 3D**（iOS SceneKit/Metal、Android Filament），而 `apps/fitme/` 现在是 **React Web**。这两条路的 3D 实现完全不同，必须先勾壳：

- [ ] B 直接上 Flutter：立刻按《10》原路线，`apps/fitme/` 这个 Web 壳只当原型，不再投入。
- [ ] C 两端都维护：成本翻倍，**不建议**。

无论勾哪个，**人体模型资源（GLB + morph target）与 \(\beta\) → 网格的映射两端通用**，不得各做一套。

#### 8.7.2 同行怎么做（2026-09 查证，见图纸 10）

| 谁 | 做什么 | 用什么 | 对我们 |
| --- | --- | --- | --- |
| **Zalando** | 两张照片或视频 → 身体测量 → 3D avatar → 虚拟试衣间 + 尺码推荐 | 自研，Web / App，**不是游戏引擎** | 2018 年起步、80 人团队；早期 avatar 就是身高体重性别的统计建模（＝我们的弱档），2023 年才上照片测量，2024 年才接进试衣间。**我们的分期与其路径一致** |
| **Walmart · Zeekit** | 「选个像我的模特」，后加上传本人照片 | 实时 2D 图像分割与映射，**无 3D 网格、无布料仿真** | 解决「好不好看」，不解决「穿哪个码」 |

**一个必须认真对待的数字**（同一家 Zalando）：

- 纯尺码推荐、没有 3D（SizeFlags，Nestler et al. KDD 2021）：72 万人/组严格 A/B，尺码相关退货降 **3.8%**（鞋）、**4.3%** 与 **6.6%**（纺织品）。
- 3D 虚拟试衣间：宣称降 **40%**，但为小范围试点自报，无对照组，公司自述「受测试阶段限制」。

**由此定调**：3D 仅是展示与信任界面，不能据外部试点数据承诺本产品退货改善。**先交付选码，3D 展示仅在门禁通过后隔离验证**；资源冲突一律保选码。

#### 8.7.4 已跑通的 demo（实测数据，不是估算）

**下面这段是旧占位的实测，不是现行展示标准。** 现行标准见《14》。代码仍在 `apps/fitme/src/mannequin/`，本地 `npm run dev` 后开 `/#shape` 能看到那具程序化人台。

程序化人台用截面样条生成，没有五官和衣服。它证明滑杆和围度可以同源，客户看到的人不再用它。

由此产生一个此前没料到的结果：

| 门槛（8.7 原列） | 实测 |
| --- | --- |
| 模型来源与授权 | 旧程序化 demo 自己算网格，未用 SMPL；**不证明现行《14》展示资产已授权**，正式资源仍须逐项核验 |
| 包体积 ≤ 2 MB | 首屏 158 KB（gzip 52 KB）；人台块 536 KB（gzip 135 KB），懒加载，进捏人页才拉 |
| 低端机兜底 | **仍未验证**。CI 环境只有 SwiftShader 软件渲染，5 fps，不代表真机；上线前必须在最差目标机型实测 |

**围度与网格同源已验证**：滑杆拖动时，围度从同一条轮廓上数值积分算出，不存在「数字 81、人台看起来像 90」。默认体型（170 cm）读数 87 / 70 / 92，属正常范围；拖到两端分别约 80 / 60 / 85 与 108 / 111 / 116，也都在真实人体区间内——滑杆映射刻意做成非对称的，往瘦拖收得慢，否则会拖出腰围 47 这种不存在的身材。
